# Proof coverage: Verus, Lean, both, neither

Written 2026-11-25. Example applications are left out.

This is a read-only survey; no prover was run for it. It is taken from the project's own evidence register (`docs/requirements_evidence.toml`), the verification plan, and the header and theorem list of every hand-written Lean file. Where a Lean counterpart could not be confirmed from those, the item is under Verus only.

The two provers look at different things. Verus proves the Rust source against a model. Lean proves the same functions as extracted from the compiled crate (Aeneas, ghost code erased). The hand-written Lean files listed contain no `sorry` and no `axiom`.

Changed since: on 2026-11-25 two items of the Lean-only table were proven in Verus as well and moved to the first table (the quieted state every entry leaves, and the deadline slots' statement). For those two Verus was run: `rsk-logic` 350 verified, `rsk-kernel` 380 verified, five mutants killed. The deadline slots' statement is not a clause of `Kernel::inv`, as this survey first suggested: it is false for a few statements inside three Kernel functions, between which `inv` is required, so it is carried beside `inv` with the exempt Task named. The hold was not ported and stays in the Lean-only table.

Later the same day three more items moved to the first table. The register drivers were there already: this survey had missed the Verus contracts of `drivers.rs`; the one statement Lean had and Verus had not (which reading the time base extends) was added. The scheduler's two statements over a run and the interrupt sources' bound were proven in Lean (`Sched/Restore.lean`, `Sched/MaskFrame.lean`, `Sched/Intakes.lean`: 72 theorems, no `sorry`, the standard three axioms). Two limits of the Lean statements: the ceiling restore is over the run of the scheduler's functions and not over a stretch of the run of the Kernel's functions (the correspondence between the two runs is proven for the states reached, not for stretches); and the erased ghost history is replaced by a list of the effective intakes a stretch names, an effective intake being one that finds its source unmasked and leaves it masked.

Later again the same day the first three rows of the Verus-only table were proven in Lean in part and split: what is proven moved to the first table (`Sched/Contain.lean` 48 theorems, `Sched/Nvic.lean` 14, `Sched/ArchHw.lean` 60; no `sorry`, the standard three axioms), and what is not stays below as each row's remainder. Three limits: the hardware model is a specification with no compiled form, so its Lean text is a restatement, the same as the Verus text by reading; the entry cores are proven over the hardware trait's contract restated as a class (`HSpec`), as Verus proves them over the trait, and not over the register model; and that `Sched::select` breaks a tie by the lowest Task identifier is a premise in `Sched/Nvic.lean`, proven in Verus only.

On 2026-11-26 most of each remainder was proven in Lean (`Sched/ContainMore.lean` 20 theorems, `Sched/HwMore.lean` 13, `Sched/ArchHwA1.lean` 7, `Sched/ArchHwA1Svc.lean` 4, `Sched/ArchHwBoot.lean` 20; no `sorry`, the standard three axioms) and moved to the first table. What is still Verus only is in the three remainder rows below: the other Partitions' timer slots and timing fields under a response; BASEPRI over an interrupt entry (two attempts at `irq_entry_core` did not check); the vector lines at `boot_core`'s return; and the join of the trait's contract to the register model.

Later on 2026-11-26 three more rows moved to the first table: the Endpoint storage between entries and dispatch planning (`Sched/Plan.lean`, 12 theorems) and the time base's wrap extension (`Hw/TimeBaseProofs.lean`, 7 theorems, over `Hw/TimeBase.lean`, a new Aeneas translation of `ArchState::extend`, which the Kernel's translation does not reach). No `sorry`, the standard three axioms.

Later again on 2026-11-26 the checksums, the Config_Checker's image functions and the Generator's acceptance check moved to the first table. Aeneas does not translate a `return` inside a loop unless the loop ends its function, so the loops of `accept_v.rs` and `image_v.rs` were restructured in the Rust source (helper functions and flags; the Verus contracts unchanged and re-proven) and translated (`Tools/GenAccept.lean`, `Tools/CcImage.lean`). `Tools/CrcSpec.lean` is one definition of CRC-32 that both the Kernel's and the Config_Checker's checksum are proven against. No `sorry`, the standard three axioms.

Last on 2026-11-26 the assembly stubs moved from "proven by neither" to Lean only: a semantics of the Armv7-M instructions the stubs use, with a decoder (`Sched/Arm.lean`); the stubs' machine code as a linked binary has it, each instruction proven to be what the decoder reads (`Sched/StubCode.lean`, 110 theorems; `cargo xtask stubs <binary>` compares a binary's halfwords with the file); and for every path of every stub, the machine run on that code reaches the state the stub model's function gives (`Sched/StubRefine.lean` 78 theorems, `Sched/StubPaths.lean` 33). The proof found one difference between the model and the processor: a floating-point instruction in a handler sets CONTROL.FPCA, which the model's `vpush` and `vpop` leave. The theorems state it as an excess of 0 or 4 on CONTROL and on the R2 `rsk_irq_entry` hands its Rust half. `rsk_timer_entry` is linked in no binary (nothing refers to it), so its code in the Lean file is assembled by hand and compared with none.

After that, the same day, on the user's word: the two stub models' `vpush` and `vpop` set CONTROL.FPCA (`fpca`; the Verus theorems that said CONTROL is as it was at the entry now say `entry_control`, which has FPCA set when the entry stacked a floating-point frame), so the machine-code theorems are exact and carry no excess (`StubCode.lean` 103 theorems, `StubPaths.lean` 28); `rsk_timer_entry`, which no vector used, was removed with its Rust half, its shell, its justification and its model in both provers; and the Link_Checker's main-stack bound counts a handler preempted at its entry instruction and a HardFault or NMI taken in a handler or in the start.

Then, of what the stubs' proof still assumed: the exception model was written over the machine (`Sched/ArmExc.lean`) and the stub model's three statements of it proven (`Sched/StubExc.lean`, 7 theorems: `excEntry_hwEntry`, `excEntry_sim`, `excReturn_sim`); every path theorem gained the statement that no exception of configurable priority can be taken between its instructions (`Sched/StubMask.lean`, 12 theorems; `AlongRun`); and the decoders were compared with LLVM's disassembler. Two more differences between the model and the architecture came out and were corrected in both stub models: the exception entry kept R0 to R3, R12 and the Z flag, which the architecture leaves UNKNOWN, and the return kept Z, which the processor restores from the stacked xPSR. The comparison with LLVM found the decoders accepting encodings the manual gives as UNPREDICTABLE or reserved; they refuse them now.

Then `rsk`, the Partition API, which stood in the last table with nothing proven: the crate is verified by Verus (60 verified) against a specification of the supervisor-call interface that the Kernel's handler is proven against too (`crates/rsk-kernel/src/arch/cm4/svc_abi.rs`; `rsk-kernel` 395 verified). It moved to the Verus-only table; what is still not proven of it has its own row in the last.

Then eight components at once, by agents working in separate copies of the tree, stopped before they reported and brought in afterwards: the rows marked 2026-11-26 in the first and third tables. What was checked of that work when it was brought in: every Verus crate verifies in the merged tree and every Lean library builds; the patches add no `sorry`, axiom, `admit` or `assume`; no existing contract line was removed without a stronger one in its place (the Kernel's were read line by line). What was not: the new statements were read in sample only (the theorems this document names), the axioms of the new Lean theorems were not printed, and the 59 mutants the agents registered were not run in the merged tree. Until that is done these rows record what the work states, not a review of it.

The columns "can it be proven on the other platform" and "would it be useful" are judgments made for this survey from the same sources, not results: nothing in them was attempted. "Useful" weighs what the second proof would add against what already stands in for it.
