# Requirements Document

## Introduction

This spec defines a command-line tool and Python library that infers a JSON Schema from a collection of JSON documents using data-mining and machine-learning techniques. It is a solo semester project, written in Python, and runs on a single laptop.

The tool infers three kinds of knowledge from the data:

- **Structure**: records versus maps (objects whose keys are really data), distinct object variants at the same location, shared base fields with add-on groups, lists versus tuples and ordered array patterns, and repeated substructures extracted into `$defs`.
- **Inter-field rules**: required versus optional fields per variant, fields that appear together, tagged unions ("if `type` is X, these fields appear"), mutually exclusive groups, keys, and references.
- **Values**: latent types hidden in strings (numbers, dates), formats, patterns, enums only when the value set is closed, and ranges that generalize beyond the observed extremes.

Guiding principles:

- Choices between alternative schemas are made with Minimum Description Length (MDL). Where a threshold is unavoidable, the threshold is learned from data rather than hard-coded.
- Judgment calls (record or map, tuple or list, enum or open, merge or split) are learned from labeled synthetic data generated from real schema corpora, augmented with weak supervision from existing heuristics.
- A corpus of real schemas suggests constraints (for example, `format: email` for a field named `email`) and identifies the closest known schema.
- Every inferred constraint carries an explanation: the method that produced the constraint, its support, and its confidence.
- A small number of bad documents does not loosen the schema. Structural change over time produces schema versions.
- Operation is fully automatic, and every technique can be toggled independently for ablation.

An evaluation harness verifies the tool: synthetic round trips on held-out schemas with negatives created by mutating the true schema, real data with known schemas as the final judge, and comparison against ReCG, JSONoid, and a naive merge. The benchmarks measure the tool; they do not define its behavior. Requirements 1–29 define the tool. Requirements 30–35 define the evaluation harness.

### Scope

Non-goals (explicitly excluded):

- Anonymized or privacy-preserving learning.
- LLM components of any kind, in inference, training, labeling, or evaluation. Classical feature-based models (decision trees, gradient boosting, shallow neural networks over hand-built features) are permitted.
- Human-in-the-loop features: no interactive review, labeling, approval, or correction steps.

Scope assumptions (proposed; confirm during review):

- The output dialect is JSON Schema draft 2020-12.
- Inference runs in batch over a finite Document_Collection. Incremental updates as new documents arrive are out of scope.
- Execution is on a single machine. Distributed execution is out of scope.
- The Schema_Corpus is drawn from SchemaStore and JSONSchemaBench.

## Glossary

Components

- **Inferrer**: The complete json-schema-inference tool, comprising the command-line interface and the Python library API.
- **Ingestor**: The component of the Inferrer that reads and parses the Document_Collection.
- **Structure_Analyzer**: The component of the Inferrer that discovers Records, Maps, Variants, Base_Fields, Field_Groups, Lists, Tuples, Array_Patterns, and Shared_Definitions.
- **Dependency_Miner**: The component of the Inferrer that discovers required fields, Co_Occurrence_Rules, Tagged_Unions, Exclusion_Rules, Key_Constraints, Reference_Constraints, and Functional_Dependencies.
- **Value_Inferrer**: The component of the Inferrer that infers JSON types, Latent_Types, Formats, Patterns, Closed_Enums, and bounds for scalar values, string lengths, array lengths, and Map sizes.
- **Outlier_Detector**: The component of the Inferrer that identifies Flagged_Items.
- **Version_Detector**: The component of the Inferrer that detects structural change points along the Ordering_Key.
- **MDL_Scorer**: The component of the Inferrer that computes the description length in bits of a candidate Schema_Model together with a set of Observations.
- **Decision_Model**: A trained classifier that predicts the outcome of one Judgment_Call kind from features computed on the observations at a Path.
- **Semantic_Type_Classifier**: A trained classifier that predicts the semantic type of the values at a scalar Path (for example email, URL, country code, currency, phone number) from value features and field-name features.
- **Corpus_Advisor**: The component of the Inferrer that suggests Constraints from the Schema_Corpus and finds the Nearest_Known_Schema.
- **Schema_Emitter**: The component of the Inferrer that serializes a Schema_Model to a JSON Schema document and writes Provenance_Records.
- **Schema_Loader**: The component of the Inferrer that parses a JSON Schema document into a Schema_Model.
- **Validator**: The component that validates JSON documents against JSON Schemas, implemented with jsonschema-rs.
- **Subschema_Checker**: The component that decides inclusion between two JSON Schemas, implemented with jsonsubschema.
- **Trainer**: The component that trains Decision_Models, the label model, the Semantic_Type_Classifier, and Learned_Thresholds, and builds the Corpus_Index, producing a Model_Bundle.
- **Synthetic_Generator**: The component that generates JSON documents from a JSON Schema together with ground-truth Judgment_Call labels derived from the schema.
- **Weak_Supervision_Module**: The component that combines Labeling_Function outputs into probabilistic labels with a label model.
- **Evaluation_Harness**: The component that runs benchmarks, baselines, ablation studies, and reports metrics.
- **Baseline_Adapter**: A wrapper that runs one Baseline on a Document_Collection and returns the Baseline's JSON Schema.

Data and structure

- **Document_Collection**: The input set of JSON documents for one inference run.
- **Observation**: One occurrence of a value at a Path in one document.
- **Path**: A location in the document tree, expressed as a sequence of object-key steps and array-element steps, where all values of a Map and all elements of a List share one wildcard step.
- **Schema_Model**: The Inferrer's internal representation of a JSON Schema together with the attached Provenance_Records.
- **Constraint**: A single assertion in an emitted schema, such as a type, a `required` entry, a Format, a Pattern, an `enum`, a bound, a branch, or a rule annotation.
- **Record**: An object node whose keys are fixed field names that belong to the schema.
- **Map**: An object node whose keys are data values (for example identifiers or dates) and whose values share one value schema.
- **Variant**: One distinct structural form of the objects observed at a single Path.
- **Object_Signature**: The set of keys of an object together with the JSON type (object, array, string, number, boolean, or null) of the value under each key.
- **Base_Fields**: The set of fields shared by every object of a Variant, or by every Variant in a family of Variants at a Path.
- **Field_Group**: A set of fields that appear together, all or none, as an add-on to the Base_Fields.
- **List**: An array whose elements are interchangeable and share one element schema regardless of position.
- **Tuple**: An array whose element schema depends on element position.
- **Array_Pattern**: An ordered pattern over element kinds within the arrays at a Path, such as a fixed prefix followed by a repeated element kind.
- **Shared_Definition**: A subschema that occurs at two or more Paths, or recursively within itself, and is emitted once under `$defs` and referenced with `$ref`.
- **Co_Occurrence_Rule**: A rule stating that the presence of one field or Field_Group implies the presence of another field or Field_Group in the same object.
- **Tagged_Union**: A set of Variants at a Path distinguished by the value of a Discriminator.
- **Discriminator**: A scalar property whose value determines which Variant applies to an object.
- **Exclusion_Rule**: A rule stating that two or more fields or Field_Groups do not appear together in the same object.
- **Key_Constraint**: A rule stating that the values at a Path are unique within a scope, where the scope is the whole Document_Collection or each enclosing array.
- **Reference_Constraint**: A rule stating that the set of values at one Path is contained in the set of values at another Path (an inclusion dependency).
- **Functional_Dependency**: A rule stating that the value at one Path determines the value at another Path within the same object scope.
- **Latent_Type**: The type that a string value encodes, one of integer, decimal number, boolean, date, date-time, or time.
- **Format**: A value of the JSON Schema `format` keyword.
- **Pattern**: An anchored regular expression emitted under the JSON Schema `pattern` keyword.
- **Closed_Enum**: A scalar Path whose value set is judged complete, so that `enum` or `const` is emitted.
- **Flagged_Item**: A document or individual value that the Outlier_Detector excludes from Constraint inference.
- **Flagged_Document**: A document that is a Flagged_Item or contains a Flagged_Item. "Non-flagged" refers to documents, objects, and values that are not part of any Flagged_Item.
- **Ordering_Key**: The ordering of documents used for change-point detection: the document index or the values at a timestamp Path.
- **Schema_Version**: A schema that describes one contiguous segment of the Document_Collection in Ordering_Key order.

Decisions and learning

- **Decision_Point**: A choice during inference whose outcome changes the emitted schema, such as a Judgment_Call, the number of Variants, the inclusion of a rule, outlier flagging, a version split, or the acceptance of a corpus suggestion.
- **Judgment_Call**: A Decision_Point of one of these kinds: Record-or-Map, Closed-or-Open-Record, Tuple-or-List, Closed-or-Open-Enum, and Merge-or-Split.
- **Learned_Threshold**: A numeric cut-off used at a Decision_Point whose value is fitted by the Trainer and stored in the Model_Bundle.
- **Resource_Parameter**: A numeric setting that affects runtime, memory, or reporting volume (for example MinHash permutation count, sample sizes, worker count, attempt budgets, time limits) and is not a Decision_Point cut-off.
- **Labeling_Function**: A heuristic that votes on the outcome of a Judgment_Call or abstains.
- **Training_Data**: Labeled and weakly labeled examples derived from training-split and validation-split schemas and from unlabeled Document_Collections, used by the Trainer.
- **Model_Bundle**: The versioned set of trained artifacts (Decision_Models, label model, Semantic_Type_Classifier, Learned_Thresholds, Corpus_Index, training manifest) loaded by the Inferrer.
- **Technique**: An individually toggleable inference method registered with the Inferrer.
- **Fallback_Behavior**: The documented behavior applied at a Decision_Point when the Technique that normally serves the Decision_Point is disabled.
- **Baseline_Rule**: A rule of the Naive_Merge Baseline that the Inferrer applies in every run, whatever the Technique states, and that resolves no Decision_Point. There are two: the `type` rule, which lists the JSON types observed at a Path (Requirement 13, criteria 1 and 2, for scalar values), and the `required` rule of Requirement 9, criteria 1 and 2. A Baseline_Rule is not a Technique: it is not registered under Requirement 28, criterion 1, and cannot be disabled.
- **Run_Configuration**: The complete set of Technique toggles, Resource_Parameters, random seed, input options, and Model_Bundle identifier for one run.
- **Support**: For a Constraint, the number of Observations consistent with the Constraint, the number of Observations at the Constraint's Path, and the ratio of the two.
- **Confidence**: A number in [0, 1] estimating the probability that a Constraint holds for unseen documents from the same source as the Document_Collection.
- **Provenance_Record**: The explanation attached to one Constraint, containing the producer (the producing Technique, or the Fallback_Behavior or Baseline_Rule that produced the Constraint), Support, Confidence, and, where applicable, the alternatives considered and their scores.
- **Inference_Report**: The machine-readable summary of one run, including parse errors, Flagged_Items, rejected candidates and suggestions, Learned_Thresholds and Resource_Parameters used, Schema_Versions, nearest known schemas, and runtimes.

Corpus and evaluation

- **Schema_Corpus**: The collection of real-world JSON Schemas drawn from SchemaStore and JSONSchemaBench.
- **Corpus_Index**: The searchable index built from the Schema_Corpus that maps normalized field names and contexts to Constraints and supports similarity search over schemas.
- **Nearest_Known_Schema**: The Schema_Corpus schema with the highest structural similarity to the inferred schema.
- **Schema_Split**: The partition of the Schema_Corpus into training, validation, and held-out splits.
- **Held_Out_Schema**: A schema in the held-out split.
- **Positive_Document**: A document that validates against the ground-truth schema.
- **Negative_Document**: A document that the ground-truth schema rejects.
- **Mutation_Operator**: A transformation that applies one targeted change to a ground-truth schema in order to generate Negative_Documents.
- **Real_Dataset**: A Document_Collection of real documents paired with a known, independently authored schema, optionally with Negative_Documents.
- **Baseline**: One of ReCG, JSONoid, or Naive_Merge.
- **Naive_Merge**: The baseline that takes the union of observed keys and JSON types at each Path (listing `integer` instead of `number` when every observed number at the Path has a zero fractional part), marks a key as required when the key is present in every observed object at the Path, and emits no other Constraints.
- **Dataset_Group**: A set of evaluation results aggregated together in Requirement 35, either the synthetic benchmark results over Held_Out_Schemas at one training collection size (Requirement 31 criterion 11) or the Real_Dataset results, with each Real_Dataset contributing its mean over cross-validation folds.
- **Reference_Laptop**: A laptop with 8 CPU cores, 16 GB of RAM, and SSD storage running macOS or Linux (proposed; confirm against the target machine).

## Requirements

### A. Input, Output, and Core Guarantees

### Requirement 1: Document Ingestion

**User Story:** As a researcher, I want to supply JSON documents in common file layouts, so that I can run inference on a dataset without preprocessing.

#### Acceptance Criteria

1. WHEN a file with extension `.jsonl` or `.ndjson` is supplied, THE Ingestor SHALL parse each non-blank line of the file as one document, where lines are separated by LF or CRLF terminators, lines are numbered from 1, and a blank line is a line that is empty or contains only space and tab characters.
2. WHEN a directory is supplied, THE Ingestor SHALL parse every regular file at any depth of the directory tree whose extension is `.json`, `.jsonl`, or `.ndjson`, including files whose names begin with a dot and without following symbolic links, treating each `.json` file as one document (subject to criterion 3) and each `.jsonl` or `.ndjson` file as newline-delimited JSON as specified in criterion 1, and SHALL ignore files with any other extension; file extensions in this requirement are compared case-insensitively.
3. WHERE array unwrapping is enabled in the Run_Configuration, THE Ingestor SHALL treat each element of a top-level array in a `.json` file as a separate document in element order, treat a top-level empty array as contributing zero documents, and treat a `.json` file whose top-level value is not an array as one document; array unwrapping is disabled unless the Run_Configuration enables it, and it applies neither to nested arrays nor to lines of `.jsonl` or `.ndjson` files.
4. THE Ingestor SHALL accept documents encoded in UTF-8, with or without a single leading byte order mark, whose top-level value is any JSON type: object, array, string, number, boolean, or null.
5. THE Ingestor SHALL assign each successfully parsed document an index from a sequence of consecutive integers starting at 0 in input order, where files are ordered by their path relative to the supplied directory compared lexicographically by Unicode code point, documents within a `.jsonl` or `.ndjson` file are ordered by line number, and documents produced by array unwrapping are ordered by element position, so that identical input files and an identical Run_Configuration produce identical indices on every run.
6. IF the primary parser rejects a document that conforms to RFC 8259, such as a document containing an integer outside the 64-bit range, THEN THE Ingestor SHALL parse the document with an RFC 8259–conformant fallback parser and include the result in the Document_Collection with every integer value preserved exactly.
7. IF a document fails to parse with both parsers, or a file found under a supplied directory cannot be read, THEN THE Ingestor SHALL skip that document or file, record in the Inference_Report the file path, the 1-based line number at which the error was detected (omitted for an unreadable file), and a description of the error, include the skipped item in a total count of skipped documents and files in the Inference_Report, and continue ingestion with the next document or file.
8. IF ingestion completes with zero successfully parsed documents, including when a supplied directory contains no file with a supported extension or every line of every supplied file is blank, THEN THE Inferrer SHALL emit no schema, exit the command-line interface with a non-zero status or raise an error from the library API, and report an error message stating that no valid documents were found.
9. WHEN a file with extension `.json` is supplied, THE Ingestor SHALL parse the entire content of the file as one document, except where array unwrapping applies as specified in criterion 3.
10. IF a supplied path does not exist, cannot be read, or is a file whose extension is not `.json`, `.jsonl`, or `.ndjson`, THEN THE Inferrer SHALL ingest no document, emit no schema, exit the command-line interface with a non-zero status or raise an error from the library API, and report an error message identifying the path and the reason it was rejected.
11. IF a document contains a construct that RFC 8259 does not permit, such as `NaN`, `Infinity`, `-Infinity`, a comment, a trailing comma, a single-quoted string, more than one top-level value, or a byte sequence that is not valid UTF-8, THEN THE Ingestor SHALL treat the document as having failed to parse with both parsers and handle it as specified in criterion 7.

### Requirement 2: Schema Emission, Loading, and Round Trip

**User Story:** As a researcher, I want emitted schemas to be standard JSON Schema that the tool can also load back, so that I can validate data with any compliant validator and compare schemas reliably.

#### Acceptance Criteria

1. THE Schema_Emitter SHALL emit each schema document, including each Schema_Version, with `$schema` set to `https://json-schema.org/draft/2020-12/schema` in the root schema object and in no subschema, such that the document validates against the draft 2020-12 meta-schema when checked with the Validator.
2. THE Schema_Emitter SHALL prefix with `x-` every emitted keyword that the draft 2020-12 vocabularies do not define, including every annotation added by the Inferrer such as `x-latent-type`, `x-array-pattern`, and `x-provenance`, where property names under `properties`, `patternProperties`, and `dependentRequired` and definition names under `$defs` are not keywords.
3. THE Schema_Emitter SHALL serialize each schema document as UTF-8 with a fixed whitespace layout, ordering object keys and the elements of `required`, `enum`, `type`, and `dependentRequired` lists by a rule that depends only on the Schema_Model content and not on the order in which Constraints were added, so that Schema_Models that are equal as defined in criterion 7 and have equal Provenance_Records produce byte-identical output.
4. THE Schema_Loader SHALL parse the keywords `type`, `properties`, `required`, `additionalProperties`, `patternProperties`, `propertyNames`, `items`, `prefixItems`, `contains`, `enum`, `const`, `format`, `pattern`, `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `minLength`, `maxLength`, `minItems`, `maxItems`, `minProperties`, `maxProperties`, `uniqueItems`, `anyOf`, `oneOf`, `allOf`, `not`, `if`, `then`, `else`, `dependentRequired`, `$defs`, and local `$ref`, together with the boolean schemas `true` and `false` at every subschema position, into a Schema_Model, where a local `$ref` is a `$ref` whose value is `#` or `#` followed by a JSON Pointer that resolves within the same document, including recursive references.
5. WHEN a schema declares the `$schema` URI of draft-04, draft-06, draft-07, or draft 2019-09, THE Schema_Loader SHALL translate the draft-specific keywords into draft 2020-12 keywords in the Schema_Model by converting `definitions` to `$defs` and rewriting each local `$ref` into `#/definitions/` to target `#/$defs/`, array-form `items` to `prefixItems`, `additionalItems` accompanying array-form `items` to `items`, array-valued `dependencies` entries to `dependentRequired`, draft-04 `id` to `$id`, and draft-04 boolean `exclusiveMinimum` or `exclusiveMaximum` together with `minimum` or `maximum` to numeric `exclusiveMinimum` or `exclusiveMaximum`, and SHALL discard, recording each discarded keyword with its JSON Pointer as ignored, the keywords that the declared draft ignores: `additionalItems` without array-form `items` and, for draft-04 through draft-07, every keyword adjacent to `$ref`.
6. IF a schema contains a construct outside the supported set, THEN THE Schema_Loader SHALL omit the construct from the Schema_Model, load the remainder of the schema, record each unsupported construct with its keyword and JSON Pointer location, and mark the Schema_Model as partially supported, where the supported set is `$schema`, the keywords in criteria 4 and 10, and the draft-specific keywords translated in criterion 5; unsupported constructs are every other keyword defined by draft 2020-12 or by the declared draft (such as `multipleOf`, `dependentSchemas`, `unevaluatedProperties`, `minContains`, `contentEncoding`, `$dynamicRef`, `$dynamicAnchor`, and `$recursiveRef`), a remote `$ref`, a local `$ref` that does not resolve, `$id` or `$anchor` below the root, schema-valued `dependencies` entries, and a `$schema` URI other than those of draft-04, draft-06, draft-07, draft 2019-09, and draft 2020-12; a Schema_Model with no recorded unsupported construct is fully supported.
7. FOR ALL Schema_Models produced by the Inferrer, including each Schema_Version, emitting the Schema_Model with the Schema_Emitter and loading the emitted document with the Schema_Loader SHALL produce a fully supported Schema_Model equal to the original, where two Schema_Models are equal when they contain the same keywords with equal values at the same JSON Pointer locations, with `required`, `enum`, `type`, and `dependentRequired` lists compared as sets, and with `$schema`, Provenance_Records, `x-provenance` annotations, and the Schema_Loader's records of ignored keywords and assumed dialect excluded from the comparison (round-trip property).
8. FOR ALL fully supported schemas in the Schema_Corpus, loading with the Schema_Loader, emitting with the Schema_Emitter, and loading the emitted document again SHALL produce a Schema_Model equal, as defined in criterion 7, to the first loaded Schema_Model (round-trip property).
9. FOR ALL fully supported SchemaStore schemas with positive or negative test files, validating each test document with the Validator against the original schema under its declared draft and against the emitted form of the loaded schema, with `format` treated as an assertion for both, SHALL yield the same accept-or-reject verdict for every test document (semantic preservation property).
10. THE Schema_Loader SHALL retain the annotation keywords `title`, `description`, `default`, `examples`, `deprecated`, `readOnly`, `writeOnly`, and `$comment`, the root `$id`, and every `x-` prefixed keyword in the Schema_Model, and SHALL omit every other keyword that neither draft 2020-12 nor the declared draft defines (for example `markdownDescription`), recording each omitted keyword with its JSON Pointer as ignored without marking the Schema_Model as partially supported.
11. IF a schema declares no `$schema` keyword at its root, or declares a `$schema` URI other than those of draft-04, draft-06, draft-07, draft 2019-09, and draft 2020-12, THEN THE Schema_Loader SHALL interpret the schema as draft 2020-12 and record in the Schema_Model that the dialect was assumed rather than declared.
12. IF a document passed to the Schema_Loader is not valid JSON, has a root that is neither a JSON object nor a boolean, or fails validation with the Validator against the meta-schema of its declared or assumed draft, THEN THE Schema_Loader SHALL return an error indicating which of these checks failed, including the line and column for a JSON syntax error, and SHALL return no Schema_Model.

### Requirement 3: Soundness on Non-Flagged Documents

**User Story:** As a researcher, I want the inferred schema to accept the data the schema was inferred from, apart from documents set aside as outliers, so that the schema faithfully describes the data.

#### Acceptance Criteria

1. FOR ALL Document_Collections and all Run_Configurations, every parsed document that is not a Flagged_Document SHALL validate, under the Validator with `format` treated as an assertion, against the emitted schema of the Schema_Version that covers the document, or against the single emitted schema when no change point is accepted, and, when Schema_Versions are emitted, against the combined schema (soundness property).
2. WHEN Constraint inference finishes, and before the Schema_Emitter writes any schema, THE Inferrer SHALL validate with the Validator, treating `format` as an assertion, every parsed document that is not a Flagged_Document, including documents left out of any sample drawn under Requirement 29 criterion 8, against the schema of the Schema_Version that covers the document or against the single schema when no change point is accepted, and SHALL exclude every Flagged_Document from this validation.
3. IF a document that is not a Flagged_Document fails the validation in criterion 2, THEN THE Inferrer SHALL relax one or more of the Constraints that the Validator reports as failing for the document, only within the schema that covers the document, by replacing each such Constraint with a Constraint that accepts the document or by removing it, subject to criterion 5, choosing among the candidate relaxations that make the document validate by the procedure of Requirement 28 criteria 6 and 7, and SHALL then repeat the validation until every document that is not a Flagged_Document validates or the pass limit of criterion 7 is reached.
4. WHEN the validation and relaxation of criteria 2, 3, and 7 finish, THE Inferrer SHALL record in the Inference_Report, for each Schema_Version or for the single emitted schema, the number of Flagged_Documents, the number of documents validated in criterion 2, the number of documents that failed the first validation pass, the number of relaxations applied in criterion 3, the number of Constraints removed in criterion 7, the number of validation passes performed, and whether the pass limit of criterion 7 was reached, reporting zero for every count with no occurrences.
5. FOR ALL relaxations and removals applied in criteria 3 and 7, every document that validated against the covering schema before the change SHALL validate against the covering schema after the change (monotonicity property).
6. WHEN a Constraint is relaxed or removed in criterion 3 or 7, THE Inferrer SHALL record the Constraint before the change, the Constraint after the change or an indication of removal, the indices of the documents that triggered the change, and, for changes made in criterion 3, the candidate relaxations considered with their scores, in the Provenance_Record of a relaxed Constraint or in the Inference_Report for a removed Constraint, with the Support of a relaxed Constraint recomputed after the change.
7. IF a document that is not a Flagged_Document still fails validation when the number of validation passes in criterion 3 reaches the maximum pass count set as a Resource_Parameter, where one pass is one validation of every document that is not a Flagged_Document, THEN THE Inferrer SHALL remove each Constraint that the Validator reports as failing for such a document, repeating removal and validation until every document that is not a Flagged_Document validates, before the Schema_Emitter writes any schema.

### B. Structure Discovery

### Requirement 4: Records Versus Maps

**User Story:** As a researcher, I want objects whose keys are really data (such as IDs or dates) recognized as maps, so that the schema describes the shared value structure instead of listing every observed key.

#### Acceptance Criteria

1. WHEN non-flagged objects containing at least one key are observed at a Path, THE Structure_Analyzer SHALL resolve the Record-or-Map Judgment_Call for the Path to exactly one of Record or Map and SHALL attach to the resulting Constraint a Provenance_Record naming the producing Technique, the Confidence, and the rejected alternative with its score.
2. WHEN a Path is classified as Record, THE Schema_Emitter SHALL list under `properties` exactly the keys that occur in at least one non-flagged object at the Path, each with a subschema inferred from the non-flagged values of that key.
3. WHEN a Path is classified as Map, THE Schema_Emitter SHALL emit exactly one value schema under `additionalProperties`, inferred at the wildcard step of the Path from the non-flagged values of all keys at the Path, and SHALL emit no `properties` or `required` entries for the Path.
4. WHEN a Path is classified as Map and the Value_Inferrer infers a Format or Pattern from the keys of the non-flagged objects at the Path, using the Format detection of Requirement 13 and the Pattern induction of Requirement 14, THE Schema_Emitter SHALL emit the inferred key Constraint under `propertyNames` such that every key of every non-flagged object at the Path satisfies the Constraint.
5. WHERE the hybrid Record/Map partitioning Technique is enabled, WHEN non-flagged objects containing at least one key are observed at a Path, THE Structure_Analyzer SHALL partition the keys at the Path into Record fields and Map entries, assigning every observed key to exactly one of the two sets and replacing the Record-or-Map outcome of criterion 1 for the Path, if and only if the partitioned encoding has a lower description length, as computed by the MDL_Scorer, than both the all-Record and the all-Map encodings.
6. WHEN the keys at a Path are partitioned into Record fields and Map entries, THE Schema_Emitter SHALL emit the Record fields under `properties` and one value schema for the Map entries under `patternProperties`, keyed by the Pattern inferred for the Map entry keys, if the Value_Inferrer infers a Pattern that matches every Map entry key and no Record field name, or under `additionalProperties` otherwise.
7. WHEN a Path is classified as Record, or is partitioned under criterion 5 with the Map entries emitted under `patternProperties`, THE Structure_Analyzer SHALL resolve the Closed-or-Open-Record Judgment_Call for the Path.
8. WHEN a Record is judged closed, THE Schema_Emitter SHALL emit `additionalProperties: false` for the Record, so that the emitted schema rejects any key that is neither listed under `properties` nor matched by a `patternProperties` Pattern.
9. WHEN a Record is judged open, THE Schema_Emitter SHALL omit `additionalProperties` for the Record, so that the emitted schema accepts keys not listed under `properties`.
10. IF the Decision_Model for the Record-or-Map Judgment_Call kind is disabled, THEN THE Structure_Analyzer SHALL resolve the Judgment_Call by selecting whichever of the Record and Map encodings has the lower description length as computed by the MDL_Scorer, selecting Record on a tie, or by classifying the Path as Record when the MDL selection Technique is also disabled.
11. IF no non-flagged object at a Path contains any key, THEN THE Structure_Analyzer SHALL classify the Path as Record with no `properties` entries without resolving the Record-or-Map Judgment_Call and SHALL record in the Provenance_Record that no keys were available to evaluate.

### Requirement 5: Object Variants and Merge-or-Split

**User Story:** As a researcher, I want different kinds of objects that appear at the same location separated into variants, so that each variant gets precise rules instead of one loose union.

#### Acceptance Criteria

1. WHEN the non-flagged objects observed at a Path have two or more distinct Object_Signatures, THE Structure_Analyzer SHALL partition the non-flagged objects at the Path into candidate Variants so that each non-flagged object belongs to exactly one candidate Variant and objects with identical Object_Signatures belong to the same candidate Variant.
2. THE Structure_Analyzer SHALL select the number of Variants at a Path, from 1 up to the number of distinct Object_Signatures among the non-flagged objects at the Path, by minimizing description length with the MDL_Scorer, or, for mixture-model Techniques, by minimizing BIC over component counts from 1 up to the smaller of that number and a maximum component count set as a Resource_Parameter, without reading a Variant count from the Run_Configuration.
3. WHEN two or more candidate Variants exist at a Path, THE Structure_Analyzer SHALL resolve the Merge-or-Split Judgment_Call so that each candidate Variant is either kept as a separate Variant or merged with one or more other candidate Variants, using the predicted class of the Merge-or-Split Decision_Model when that Decision_Model is enabled and otherwise the alternative with the lowest description length computed by the MDL_Scorer.
4. WHEN the Merge-or-Split Judgment_Call at a Path yields two or more Variants, THE Schema_Emitter SHALL emit exactly one object-schema branch per Variant under `anyOf`, each branch declaring under `properties` only the fields observed in the non-flagged objects of that Variant.
5. WHEN every pair of branches emitted for the Variants at a Path is disjoint, meaning that both branches of the pair require a common property and constrain it to non-overlapping `const` or `enum` value sets, or one branch of the pair requires a field that the other branch does not permit, THE Schema_Emitter SHALL emit the branches under `oneOf` instead of `anyOf`.
6. WHEN two or more candidate Variants at a Path are merged into one Variant, THE Schema_Emitter SHALL emit for the merged Variant one object schema whose `properties` contain the union of the fields of the merged candidate Variants, whose `required` list omits every field absent from at least one merged candidate Variant, and in which each field accepts every JSON type observed for the field across the merged candidate Variants.
7. WHERE the MinHash/LSH Technique is enabled, THE Structure_Analyzer SHALL form candidate Variant groups before MDL scoring from pairs of non-flagged objects at a Path that LSH retrieves as candidates and whose MinHash-estimated Jaccard similarity of key sets is at or above the Learned_Threshold for key-set similarity, with the numbers of MinHash permutations and LSH bands set as Resource_Parameters.
8. WHERE the DBSCAN, HDBSCAN, or Bernoulli-mixture Technique is enabled, THE Structure_Analyzer SHALL produce one candidate Variant grouping per enabled Technique from the Object_Signatures of the non-flagged objects at the Path, taking the DBSCAN neighborhood radius and minimum neighbor count and the HDBSCAN minimum cluster size from Learned_Thresholds, and SHALL pass every grouping to the MDL_Scorer for comparison.
9. IF DBSCAN or HDBSCAN labels non-flagged objects at a Path as noise, THEN THE Structure_Analyzer SHALL assign all noise objects that share an Object_Signature to the one existing or new candidate Variant that yields the lowest description length computed by the MDL_Scorer, without making the noise objects Flagged_Items.
10. WHILE the MinHash/LSH, DBSCAN, HDBSCAN, and Bernoulli-mixture Techniques are all disabled, THE Structure_Analyzer SHALL place all non-flagged objects at a Path in one Variant.
11. WHILE the Merge-or-Split Decision_Model and the MDL selection Technique are both disabled, THE Structure_Analyzer SHALL keep as separate Variants the candidate Variants of the grouping selected by the Technique priority order documented in the registry.

### Requirement 6: Base Fields and Add-On Groups

**User Story:** As a researcher, I want shared base fields separated from add-on field groups, so that the schema reflects how objects are composed instead of enumerating every combination.

#### Acceptance Criteria

1. WHEN the Variants at a Path have been determined, THE Structure_Analyzer SHALL identify as the Base_Fields of each Variant the set of fields present in every non-flagged object of the Variant, and as the Base_Fields of a family of Variants the intersection of the Base_Fields of the Variants emitted as branches of one `anyOf` or `oneOf` at the Path.
2. WHEN candidate Field_Groups have been produced for a Variant at a Path, THE Structure_Analyzer SHALL select the set of Field_Groups with the lowest total description length computed by the MDL_Scorer among evaluated alternatives that include the empty set and, for each Technique enabled under criteria 3 and 4, the candidates that the Technique retains after the exclusions in criterion 7.
3. WHERE the FP-growth with SLIM-style selection Technique is enabled, THE Structure_Analyzer SHALL mine, for each Variant at a Path, the key sets that contain no Base_Field and whose frequency among the non-flagged objects of the Variant is at least the FP-growth minimum support, a Resource_Parameter, and retain the key sets selected by an MDL code table as candidate Field_Groups.
4. WHERE the Boolean matrix factorization Technique is enabled, THE Structure_Analyzer SHALL factor the object-by-key presence matrix of the non-flagged objects of each Variant at a Path, restricted to keys that are not Base_Fields, with the number of factors selected by the MDL_Scorer, and report the key set of each factor as a candidate Field_Group.
5. WHEN a Variant has one or more Base_Fields, THE Schema_Emitter SHALL list every Base_Field of the Variant under `required` in the object schema of the Variant, so that every Base_Field of a family of Variants appears under `required` in every `anyOf` or `oneOf` branch of the family.
6. WHEN a Field_Group is selected for a Variant, THE Schema_Emitter SHALL emit in the object schema of the Variant one `dependentRequired` entry per member of the Field_Group, keyed by the member and listing every other member of the Field_Group.
7. IF a non-flagged object of a Variant contains at least one but not all members of a candidate Field_Group, THEN THE Structure_Analyzer SHALL exclude the candidate from selection and record in the Inference_Report the candidate's fields, the Path, the producing Technique, and the number of violating objects.
8. THE Structure_Analyzer SHALL select only Field_Groups that contain at least two fields, contain no Base_Field of the Variant, and share no field with any other Field_Group selected for the same Variant.
9. WHILE the FP-growth with SLIM-style selection Technique and the Boolean matrix factorization Technique are both disabled, THE Structure_Analyzer SHALL apply as the Fallback_Behavior the selection of no Field_Groups at every Path, so that every field that is not a Base_Field is optional and has no `dependentRequired` entry derived from a Field_Group.

### Requirement 7: Lists, Tuples, and Array Patterns

**User Story:** As a researcher, I want arrays classified as lists or tuples and ordered element patterns captured, so that the schema constrains arrays by position where position matters.

#### Acceptance Criteria

1. WHEN at least one non-flagged array with one or more elements is observed at a Path, THE Structure_Analyzer SHALL resolve the Tuple-or-List Judgment_Call for the Path using only the non-flagged arrays at the Path, and SHALL record the outcome and its Confidence in the Provenance_Record of the `items` or `prefixItems` Constraint emitted at the Path.
2. WHEN a Path is classified as List, THE Schema_Emitter SHALL emit one element schema under `items`, inferred from every non-flagged element of every non-flagged array at the Path, and SHALL NOT emit `prefixItems` for the Path.
3. WHEN a Path is classified as Tuple, THE Schema_Emitter SHALL emit under `prefixItems` one schema for each position from 0 to one less than the maximum length of the non-flagged arrays at the Path, each inferred from the non-flagged elements observed at that position.
4. WHEN a Path is classified as Tuple and no non-flagged array observed at the Path is longer than the `prefixItems` list, THE Schema_Emitter SHALL emit `items: false`.
5. WHERE the array grammar inference Technique is enabled, THE Structure_Analyzer SHALL infer, for each array Path with at least one non-flagged element, the Array_Pattern over element kinds that matches every non-flagged array at the Path and has the lowest description length computed by the MDL_Scorer among the candidate Array_Patterns, where an element kind is the JSON type of an element, with object elements further distinguished by Variant.
6. WHEN the Array_Pattern selected in criterion 5 is expressible with `prefixItems`, `items`, and `contains`, such as a fixed prefix followed by one repeated element kind, THE Structure_Analyzer SHALL construct a candidate array schema that uses `prefixItems` for the fixed prefix, `items` for the repeated portion, and `contains` for an element kind that the repeated portion requires at least once, and that accepts every non-flagged observed array at the Path and rejects every array whose sequence of element kinds does not match the Array_Pattern.
7. WHEN the Array_Pattern selected in criterion 5 is not expressible with `prefixItems`, `items`, and `contains`, such as a pattern containing a repeated group of two or more element kinds, THE Schema_Emitter SHALL emit the schema from criteria 2 through 4 at the Path and SHALL record the complete Array_Pattern, including every element kind and repetition, in an `x-array-pattern` annotation at the Path.
8. WHEN criterion 6 produces a candidate array schema for a Path, THE Structure_Analyzer SHALL select whichever of the candidate and the schema from criteria 2 through 4 has the lower description length computed by the MDL_Scorer, keeping the schema from criteria 2 through 4 on a tie, so that only the selected schema is emitted at the Path, and SHALL record the rejected schema and its description length in the Provenance_Record of the selected schema.
9. IF every non-flagged array observed at a Path is empty, THEN THE Schema_Emitter SHALL emit the array schema for the Path without `items` and without `prefixItems`, and SHALL record in the Provenance_Record of the Path's `type` Constraint that no element was observed.
10. WHERE the Tuple-or-List Decision_Model is disabled, THE Structure_Analyzer SHALL classify a Path as Tuple if the MDL selection Technique is enabled and the MDL_Scorer assigns the Tuple schema from criteria 3 and 4 a lower description length than the List schema from criterion 2, and SHALL classify the Path as List otherwise.

### Requirement 8: Shared Definitions

**User Story:** As a researcher, I want repeated substructures extracted into `$defs`, so that the schema is concise and recurring entities are named once.

#### Acceptance Criteria

1. WHEN structurally equivalent subschemas, meaning subschemas with identical Constraints when Provenance_Records are disregarded, occur at two or more distinct Paths, THE Structure_Analyzer SHALL compute with the MDL_Scorer the total description length in bits of the Schema_Model with the subschemas inlined and with the subschemas extracted into one Shared_Definition.
2. WHEN the description length computed in criterion 1 with the Shared_Definition extracted is strictly lower than with the subschemas inlined, THE Schema_Emitter SHALL emit the subschema once under `$defs` and replace the subschema at every Path where it occurs with a local `$ref` that resolves to that `$defs` entry.
3. WHEN object subschemas, including individual Variant branches, at two or more distinct Paths share at least one property name and are not structurally equivalent, THE Structure_Analyzer SHALL resolve the Merge-or-Split Judgment_Call for the subschemas, where a merge outcome yields one Shared_Definition, referenced with `$ref` from every merged Path, in which each field absent from any merged subschema is optional.
4. WHEN the Merge-or-Split Judgment_Call in criterion 3 merges object subschemas at a Path and at one or more descendant Paths of that Path (Paths of which that Path is a proper prefix), THE Schema_Emitter SHALL emit one Shared_Definition that refers to itself with a `$ref` at the shallowest merged descendant Path, so that the emitted schema contains exactly one copy of the subschema regardless of the maximum observed nesting depth and accepts objects nested deeper than that depth.
5. THE Schema_Emitter SHALL name each Shared_Definition after the object key with the most non-flagged Observations of the subschema, where the key of an Observation is the last object-key step of its Path, breaking ties by choosing the lexicographically smallest key, using a documented default name when no Path of the subschema contains an object-key step, and resolving name collisions by keeping the unsuffixed name for the colliding Shared_Definition with the most non-flagged Observations and appending the suffixes 2, 3, … to the others in descending Observation count, breaking ties by the lexicographic order of their serialized subschemas.
6. IF the description length computed in criterion 1 with the Shared_Definition extracted is equal to or greater than with the subschemas inlined, THEN THE Inferrer SHALL emit the subschema inline at every Path where it occurs and record the rejected candidate, its Paths, and both description lengths in the Inference_Report.
7. WHILE the Shared_Definition extraction Technique is disabled, THE Structure_Analyzer SHALL skip criteria 1 and 2 and skip criterion 3 for Paths of which neither is a prefix of the other, so that the emitted schema contains no `$defs` entry other than self-referencing Shared_Definitions produced under criterion 4.
8. WHILE the recursion detection Technique is disabled, THE Structure_Analyzer SHALL exclude from criterion 3 every pair of Paths in which one Path is a prefix of the other, so that no Shared_Definition in the emitted schema contains a `$ref` to itself and the subschema at each observed nesting level is emitted inline.

### C. Inter-Field Rules

### Requirement 9: Required, Optional, and Co-Occurring Fields

**User Story:** As a researcher, I want required and optional fields determined per variant and co-occurring fields captured, so that the schema states which fields must appear and which travel together.

#### Acceptance Criteria

1. THE Dependency_Miner SHALL classify each field present in at least one non-flagged object of a Variant as exactly one of required or optional for that Variant. The classification SHALL use only the non-flagged objects of that Variant, and a field is optional when it is present in at least one but not every non-flagged object of the Variant.
2. WHEN a field is present in every non-flagged object of a Variant, THE Dependency_Miner SHALL mark the field as required for the Variant. A field is present in an object when the object contains the field's key with any value, including `null`.
3. WHEN, among the non-flagged objects of a Variant, an antecedent field is present in at least one object and every object that contains the antecedent field also contains a different consequent field that is optional for the Variant, THE Dependency_Miner SHALL report a Co_Occurrence_Rule candidate stating that the antecedent field implies the consequent field.
4. WHERE the MDL selection Technique is enabled, WHEN adding a Co_Occurrence_Rule candidate that criterion 6 does not discard lowers the total description length computed by the MDL_Scorer, compared with the same Variant subschema without the candidate, THE Schema_Emitter SHALL express the Co_Occurrence_Rule, subject to criterion 5, as a `dependentRequired` entry in the Variant's subschema that requires the consequent field whenever the antecedent field is present.
5. THE Schema_Emitter SHALL emit, for each Variant, a subset of the Co_Occurrence_Rules selected under criterion 4 or criterion 8 that meets two conditions: (a) every selected Co_Occurrence_Rule can be derived by transitive chaining from the emitted subset, the Variant's `required` list, and the Field_Group `dependentRequired` entries of Requirement 6 criterion 6; (b) no emitted Co_Occurrence_Rule can be derived from the remaining emitted entries and the `required` list.
6. IF a Co_Occurrence_Rule candidate has a Support count below the Learned_Threshold for rule support, THEN THE Dependency_Miner SHALL discard the candidate without evaluating it under criterion 4 or criterion 8. The Support count is the number of non-flagged objects of the Variant that contain the antecedent field. For each discarded candidate, THE Dependency_Miner SHALL record in the Inference_Report the Path, the Variant, the antecedent field, the consequent field, the Support count, and the threshold value.
7. WHEN the required and optional fields of a Variant are determined, THE Schema_Emitter SHALL emit in the Variant's subschema a `required` list that contains every field marked required for the Variant and no field marked optional for the Variant.
8. WHERE the MDL selection Technique is disabled, WHEN a Co_Occurrence_Rule candidate that criterion 6 does not discard has a Confidence at or above the Learned_Threshold on Confidence for Co_Occurrence_Rules, THE Schema_Emitter SHALL express the Co_Occurrence_Rule as specified in criterion 4, subject to criterion 5.
9. WHERE the co-occurrence mining Technique is disabled, THE Dependency_Miner SHALL apply the Fallback_Behavior of reporting no Co_Occurrence_Rule candidates. The emitted schema then contains no `dependentRequired` entries other than those from Requirement 6 criterion 6, and it still contains the `required` lists of criterion 7.

### Requirement 10: Tagged Unions

**User Story:** As a researcher, I want discriminator fields detected ("if `type` is X, these fields appear"), so that the schema ties each variant's fields to the discriminator value.

#### Acceptance Criteria

1. WHEN a split retained under criterion 2 tests the value of a property that is present in every non-flagged object at a Path and whose values in those objects are all JSON strings, integers, or booleans, THE Dependency_Miner SHALL report the property as a Discriminator candidate for the Path and SHALL record the candidate in the Inference_Report with its description length, computed by the MDL_Scorer for the non-flagged objects at the Path partitioned by the candidate's value groups.
2. WHERE the per-field decision tree Technique is enabled, THE Dependency_Miner SHALL train decision trees on the non-flagged objects at a Path: one tree for each field-presence target (a field present in at least one but not every non-flagged object at the Path), plus one tree with Variant membership as the target at each Path where the Structure_Analyzer has split the objects into two or more Variants. The trees SHALL use the values of scalar sibling properties as categorical features, and the Dependency_Miner SHALL retain only the splits whose inclusion lowers the total description length computed by the MDL_Scorer compared with the same tree without the split.
3. WHEN one or more Discriminator candidates exist at a Path, THE Dependency_Miner SHALL select as the Path's Discriminator the candidate with the lowest description length under criterion 1. Only candidates with at least one value group whose Support ratio meets the Learned_Threshold for branch support are eligible. The Support ratio of a value group is the number of non-flagged objects at the Path carrying a value of the group divided by the number of non-flagged objects at the Path. Ties SHALL be broken by the smallest property name in Unicode code-point order, and THE Dependency_Miner SHALL record each non-selected candidate with its description length in the Inference_Report and in the Provenance_Record of the selected Discriminator.
4. WHEN a Discriminator is selected at a Path, THE Schema_Emitter SHALL emit one dedicated branch per value group whose Support ratio meets the Learned_Threshold for branch support. A value group is a maximal set of observed Discriminator values that no split retained under criterion 2 separates. Each dedicated branch SHALL constrain the Discriminator with `const` for a single-value group or `enum` for a multi-value group, and SHALL list under `required` the Base_Fields plus every field present in all non-flagged objects carrying a value of the group.
5. IF a value group of the selected Discriminator has a Support ratio below the Learned_Threshold for branch support, THEN THE Schema_Emitter SHALL cover the non-flagged objects carrying the group's values with one fallback branch that requires only the Base_Fields and constrains the Discriminator with `enum` to the values of all below-threshold value groups.
6. WHERE the per-field decision tree Technique is disabled, THE Dependency_Miner SHALL report no Discriminator candidates and select no Discriminator at any Path, so that the Schema_Emitter emits no Discriminator-constrained branches and the objects at each Path are emitted as the Variants determined under Requirement 5.
7. WHEN a Discriminator is selected at a Path, THE Schema_Emitter SHALL emit the branches so that every non-flagged object at the Path validates, as checked by the Validator, against exactly one branch.
8. IF the Value_Inferrer does not judge the Discriminator's Path to be a Closed_Enum, THEN THE Schema_Emitter SHALL emit the fallback branch of criterion 5 even when no value group falls below the Learned_Threshold for branch support, and SHALL constrain the fallback branch's Discriminator to every value not assigned to a dedicated branch instead of using the `enum` of criterion 5.

### Requirement 11: Mutually Exclusive Groups

**User Story:** As a researcher, I want mutually exclusive fields and groups detected, so that the schema rejects objects that combine alternatives.

#### Acceptance Criteria

1. WHERE the exclusion mining Technique is enabled, WHEN two or more fields or Field_Groups at a Path each appear in at least one non-flagged object at the Path and no non-flagged object at the Path contains fields from more than one of them, THE Dependency_Miner SHALL report each maximal such set as one Exclusion_Rule candidate whose members are those fields and Field_Groups, representing a field that belongs to a Field_Group at the Path only through that Field_Group.
2. THE Dependency_Miner SHALL compute the Confidence of each Exclusion_Rule candidate as a value in [0, 1] that strictly increases with the number of non-flagged objects at the Path expected to contain two or more members if member presences were independent, so that at the same Path a candidate with a larger expected count receives higher Confidence than a candidate with a smaller expected count, and SHALL report the expected count alongside the Confidence in the Provenance_Record of the emitted Exclusion_Rule or in the Inference_Report entry of a discarded candidate.
3. IF no emitted Variant branch or Tagged_Union branch at the Path accepts an object that contains fields from two or more members of an Exclusion_Rule candidate, THEN THE Dependency_Miner SHALL discard the candidate as already enforced and record the candidate and the enforcing branches in the Inference_Report.
4. IF an Exclusion_Rule candidate not discarded under criterion 3 neither reduces total description length as computed by the MDL_Scorer nor has Confidence at or above the Learned_Threshold on Confidence for Exclusion_Rules, THEN THE Dependency_Miner SHALL discard the candidate and record the rejection, with the candidate's members and Confidence, in the Inference_Report.
5. WHEN an Exclusion_Rule candidate is not discarded under criterion 3 or 4 and every non-flagged object at the Path contains fields from exactly one member, THE Schema_Emitter SHALL express the Exclusion_Rule as a `oneOf` with one branch per member, each branch requiring the fields of that member.
6. WHEN an Exclusion_Rule candidate is not discarded under criterion 3 or 4 and at least one non-flagged object at the Path contains fields from no member, THE Schema_Emitter SHALL express the Exclusion_Rule as one `not` over the combined `required` set of each pair of members.
7. WHERE the exclusion mining Technique is disabled, THE Dependency_Miner SHALL apply the Fallback_Behavior of reporting no Exclusion_Rule candidates, so that the Schema_Emitter emits no Constraint produced by an Exclusion_Rule.

### Requirement 12: Keys, References, and Functional Dependencies

**User Story:** As a researcher, I want unique keys, references between fields, and functional dependencies discovered, so that the schema documents identity and linkage in the data.

#### Acceptance Criteria

1. WHERE the key discovery Technique is enabled, WHEN a scalar Path holds at least two non-flagged values and every non-flagged value at the Path is distinct across the Document_Collection, THE Dependency_Miner SHALL report a Key_Constraint candidate with collection scope. Values are compared by JSON Schema instance equality: numbers compare by mathematical value, so `1` equals `1.0`; values of different JSON types are distinct; `null` counts as a value; and an absent field contributes no value.
2. WHERE the key discovery Technique is enabled, WHEN at least one nearest enclosing array holds two or more non-flagged values at a scalar Path inside array elements, and every non-flagged value at the Path is distinct within each nearest enclosing array but not across the Document_Collection, THE Dependency_Miner SHALL report a Key_Constraint candidate with array scope. Values are compared with the equality defined in criterion 1.
3. WHERE the functional and inclusion dependency discovery Technique is enabled, WHEN the non-empty set of non-flagged values at a Path is contained in the set of non-flagged values at a different Path that holds a selected Key_Constraint, THE Dependency_Miner SHALL report a Reference_Constraint candidate from the first Path to the Key_Constraint Path. Values are compared with the equality defined in criterion 1. In this requirement, a selected candidate of any kind is one not discarded under criterion 6.
4. WHERE the functional and inclusion dependency discovery Technique is enabled, WHEN all three of the following hold, THE Dependency_Miner SHALL report a Functional_Dependency candidate from A to B:
   - Two distinct Paths A and B lie within the same object, with no array-element or Map wildcard step between that object and either Path.
   - Across the non-flagged objects that contain both Paths, every value at A co-occurs with exactly one value at B, using the equality defined in criterion 1.
   - At least one value at A occurs in two or more of those objects.
5. THE Dependency_Miner SHALL compute the Confidence of each Key_Constraint, Reference_Constraint, and Functional_Dependency candidate from the probability that the observed pattern arises by chance, given the number of Observations and the number of distinct values. Between two candidates of the same kind with the same ratio of distinct values to Observations, the candidate with more Observations SHALL receive a Confidence greater than or equal to the other candidate's.
6. IF the Confidence of a Key_Constraint, Reference_Constraint, or Functional_Dependency candidate is below the Learned_Threshold for the candidate's kind, THEN THE Dependency_Miner SHALL discard the candidate and record the following in the Inference_Report: the candidate's kind, its Paths, its scope where applicable, its Confidence, and the Learned_Threshold value.
7. WHEN a selected Key_Constraint of either scope is at the element Path of a List whose non-flagged elements are all scalars, THE Schema_Emitter SHALL emit `uniqueItems: true` for the List.
8. THE Schema_Emitter SHALL emit selected candidates as annotations, and SHALL NOT emit `uniqueItems` for a Key_Constraint at a field of object elements:
   - Each selected Key_Constraint as an `x-key` annotation on the subschema of the key Path, stating the scope.
   - Each selected Reference_Constraint as an `x-references` annotation on the subschema of the referencing Path, identifying the referenced Path.
   - Each selected Functional_Dependency as an `x-functional-dependency` annotation on the subschema of the enclosing object, identifying the determinant and dependent Paths.
9. WHERE the key discovery Technique is disabled, THE Dependency_Miner SHALL apply as the Fallback_Behavior reporting no Key_Constraint candidates. As a result, the emitted schema contains no `x-key` annotations, no `uniqueItems` derived from Key_Constraints, and no `x-references` annotations.
10. WHERE the functional and inclusion dependency discovery Technique is disabled, THE Dependency_Miner SHALL apply as the Fallback_Behavior reporting no Reference_Constraint or Functional_Dependency candidates. As a result, the emitted schema contains no `x-references` or `x-functional-dependency` annotations.

### D. Value Inference

### Requirement 13: Types, Latent Types, and Formats

**User Story:** As a researcher, I want real value types detected, including numbers and dates hidden in strings, so that the schema describes what values mean and not only how they are encoded.

#### Acceptance Criteria

1. THE Value_Inferrer SHALL emit, for each scalar Path, a `type` Constraint listing exactly the JSON types of the non-flagged values at the Path, drawn from `string`, `number`, `integer`, `boolean`, and `null`, with numbers listed as `integer` under criterion 2 and as `number` otherwise, never both.
2. WHEN every non-flagged number at a Path has a zero fractional part, including integral values written with a decimal point or exponent such as `1.0` or `1e3`, THE Value_Inferrer SHALL emit `integer` instead of `number` for the Path.
3. WHERE the latent-type detection Technique is enabled, WHEN a Path has at least one non-flagged string and every non-flagged string at the Path encodes the same Latent_Type, THE Value_Inferrer SHALL record the Latent_Type in an `x-latent-type` annotation, keep `string` as the JSON type of those values, and produce as a candidate the `date`, `date-time`, or `time` Format when every such string satisfies that Format and a Pattern matching every such string otherwise, treating a mix of integer and decimal-number strings as the Latent_Type decimal number.
4. WHERE the Format detection Technique is enabled, THE Value_Inferrer SHALL produce, for each Path, a candidate for each of the Formats `date-time`, `date`, `time`, `duration`, `email`, `hostname`, `ipv4`, `ipv6`, `uri`, and `uuid` that at least one non-flagged string at the Path satisfies, where a string satisfies a Format if and only if the Validator, with format assertion enabled, accepts the string for that Format.
5. WHERE the Semantic_Type_Classifier Technique is enabled, THE Value_Inferrer SHALL predict, for each scalar Path with at least one non-flagged string, a semantic type and its calibrated probability from value features and field-name features, and produce as a candidate the Format or Pattern that the Semantic_Type_Classifier maps to the predicted semantic type.
6. IF a candidate Format or Pattern from criteria 3–5 rejects one or more non-flagged strings at the Path when checked by the Validator with format assertion enabled, THEN THE Value_Inferrer SHALL withhold the candidate, keep the other Constraints of the Path, and record in the Inference_Report the Path, the candidate, the producing Technique, and the count of rejected non-flagged strings.
7. IF the calibrated probability of the semantic type predicted for a Path is below the Learned_Threshold for semantic-type acceptance, or the Semantic_Type_Classifier maps the predicted semantic type to no Format or Pattern, THEN THE Value_Inferrer SHALL produce no candidate from the Semantic_Type_Classifier for the Path and record the predicted semantic type and its probability in the Inference_Report.
8. WHEN one or more candidates from criteria 3–5 satisfy every non-flagged string at a Path, THE Value_Inferrer SHALL emit the satisfying candidate with the lowest description length computed by the MDL_Scorer as the only Format or Pattern from these criteria at the Path, and list each other satisfying candidate as an alternative in the Provenance_Record of the emitted Constraint.
9. WHERE the latent-type detection, Format detection, or Semantic_Type_Classifier Technique is disabled, THE Value_Inferrer SHALL apply the Fallback_Behavior of producing no `x-latent-type` annotation and no candidate from the disabled Technique, with criteria 1 and 2 and the enabled Techniques among criteria 3–5 applying unchanged.

### Requirement 14: String Pattern Induction

**User Story:** As a researcher, I want syntactic patterns inferred for structured strings such as codes and identifiers, so that the schema constrains string shape where no standard format applies.

#### Acceptance Criteria

1. WHERE the pattern induction Technique is enabled, THE Value_Inferrer SHALL induce candidate Patterns, each a disjunction of one or more sub-patterns with the number of sub-patterns not exceeding a maximum set as a Resource_Parameter, for the non-flagged string values at each Path that has at least one non-flagged string value, has no selected Format, and is not a Closed_Enum, and for the keys at each Map Path that has no selected key Format.
2. WHEN candidate Patterns are induced for a Path, THE Value_Inferrer SHALL select, from the candidate Patterns of different specificity retained under criterion 7 and the option of emitting no Pattern, the alternative with the minimum description length computed by the MDL_Scorer, resolving equal description lengths first in favor of emitting no Pattern and then in favor of the candidate with fewer sub-patterns.
3. FOR ALL emitted Patterns, every non-flagged string value or Map key at the Pattern's Path SHALL match the Pattern as evaluated by the Validator (soundness property).
4. THE Value_Inferrer SHALL anchor every emitted Pattern at the start and the end of the string, such that under ECMA-262 and Python `re` search semantics the Pattern matches a string only when the expression matches the entire string, including any trailing line terminator.
5. THE Value_Inferrer SHALL emit Patterns using only regular-expression syntax for which ECMA-262, Python `re`, and the Validator return the same match result for every input string, including strings that contain non-ASCII characters or line terminators (dialect-agreement property).
6. WHERE the pattern induction Technique is disabled, THE Value_Inferrer SHALL emit no Pattern produced by pattern induction at any Path and SHALL emit unchanged the Patterns produced by latent-type detection and the Semantic_Type_Classifier under Requirement 13.
7. IF a candidate Pattern, including a candidate induced from a sample of the values at a Path, fails to match one or more non-flagged string values or Map keys at the Path as evaluated by the Validator, THEN THE Value_Inferrer SHALL discard the candidate and record in the Inference_Report the Path, the candidate, and the number of non-matching strings.
8. IF the number of candidate Patterns evaluated at a Path reaches the per-Path attempt budget set as a Resource_Parameter, THEN THE Value_Inferrer SHALL stop induction at the Path, apply the selection of criterion 2 to the candidates evaluated so far, and record the exhausted budget for the Path in the Inference_Report.

### Requirement 15: Closed Enumerations

**User Story:** As a researcher, I want enums emitted only when the value set is actually closed, so that the schema does not reject legitimate unseen values.

#### Acceptance Criteria

1. WHERE the Good–Turing/Chao1 enum estimation Technique is enabled, WHEN a scalar Path has one or more non-flagged scalar Observations, THE Value_Inferrer SHALL compute over those Observations the observation count n, the distinct value count S_obs, the count f1 of values observed exactly once, the count f2 of values observed exactly twice, the Good–Turing unseen-mass estimate f1/n, and the Chao1 estimate S_obs + f1²/(2·f2), or S_obs + f1·(f1 − 1)/2 when f2 is 0. Two values count as the same distinct value when they are equal under draft 2020-12 `enum` equality (for example, `1` and `1.0`).
2. WHERE the Good–Turing/Chao1 enum estimation Technique and the Closed-or-Open-Enum Decision_Model are both enabled, THE Value_Inferrer SHALL resolve the Closed-or-Open-Enum Judgment_Call for each scalar Path with that Decision_Model, and the Decision_Model's input features SHALL include the six statistics from criterion 1.
3. WHEN a Path is judged a Closed_Enum, THE Schema_Emitter SHALL emit `const` holding the single distinct value if S_obs from criterion 1 equals 1, and otherwise SHALL emit `enum` containing exactly the distinct non-flagged scalar values observed at the Path, with no value listed twice under the equality defined in criterion 1.
4. WHEN a Path is judged open, THE Schema_Emitter SHALL emit no `enum` or `const` Constraint for the Path and SHALL still emit the type, Format, Pattern, and bound Constraints inferred for the Path.
5. IF every distinct non-flagged scalar value at a Path is observed exactly once (f1 equals S_obs), or the Path has no non-flagged scalar Observation, THEN THE Value_Inferrer SHALL judge the Path open, overriding the outcome of criterion 2 or criterion 6.
6. WHERE the Good–Turing/Chao1 enum estimation Technique is enabled and the Closed-or-Open-Enum Decision_Model is disabled, THE Value_Inferrer SHALL resolve the Closed-or-Open-Enum Judgment_Call for each scalar Path by using the MDL_Scorer to select whichever of the Closed_Enum candidate and the open candidate has the lower description length. The Closed_Enum candidate SHALL be charged an exception cost for unseen values whose total probability equals the Good–Turing estimate from criterion 1, and the Path SHALL be judged open when the two description lengths are equal.
7. WHERE the Good–Turing/Chao1 enum estimation Technique is disabled, THE Value_Inferrer SHALL apply as the Fallback_Behavior of the Closed-or-Open-Enum Judgment_Call the rule of judging every scalar Path open, whether or not the Closed-or-Open-Enum Decision_Model is enabled.
8. WHEN the Closed-or-Open-Enum Judgment_Call is resolved for a Path for which criterion 1 computed statistics, THE Value_Inferrer SHALL record the six statistics, the outcome, and the identifier of the resolving Technique. For a Closed_Enum, the record SHALL go in the Provenance_Record of the emitted `enum` or `const` Constraint. For a Path judged open, the record SHALL go in the Inference_Report as a rejected enum candidate.

### Requirement 16: Ranges and Size Bounds

**User Story:** As a researcher, I want sensible numeric ranges and size bounds, so that the schema catches out-of-range values without overfitting to the observed extremes.

#### Acceptance Criteria

1. WHERE the bound generalization Technique is enabled, WHEN one or more non-flagged JSON numbers are observed at a Path that is not a Closed_Enum, THE Value_Inferrer SHALL decide separately for `minimum` and for `maximum` whether to emit the bound and which value to emit, using the selection of criterion 2 over the non-flagged JSON numbers at the Path.
2. WHEN the Value_Inferrer decides a bound over a set of observed quantities, THE Value_Inferrer SHALL select, with the MDL_Scorer, the candidate with the lowest description length from exactly these candidates: omitting the bound; the observed extreme; zero; the observed extreme rounded outward (a minimum toward negative infinity, a maximum toward positive infinity) to one and to two significant digits, so that an observed maximum of 137 yields 200 and 140; and, when every observed quantity is an integer, each lower limit (for a minimum) or upper limit (for a maximum) of the signed and unsigned 8-, 16-, 32-, and 64-bit integer ranges. Before selection, it SHALL exclude every candidate that any observed quantity violates and, for string lengths, array lengths, and Map key counts, every negative candidate.
3. WHERE the bound generalization Technique is enabled, WHEN one or more non-flagged strings are observed at a Path that has no selected Format and is not a Closed_Enum, THE Value_Inferrer SHALL decide separately for `minLength` and for `maxLength` whether to emit the bound and which value to emit, using the selection of criterion 2 over the lengths of the non-flagged strings measured in Unicode code points.
4. WHERE the bound generalization Technique is enabled, WHEN one or more non-flagged arrays are observed at a Path, THE Value_Inferrer SHALL decide separately for `minItems` and for `maxItems` whether to emit the bound and which value to emit, using the selection of criterion 2 over the element counts of the non-flagged arrays at the Path.
5. WHERE the bound generalization Technique is enabled, WHEN a Path is classified as Map, THE Value_Inferrer SHALL decide separately for `minProperties` and for `maxProperties` whether to emit the bound and which value to emit, using the selection of criterion 2 over the key counts of the non-flagged objects at the Path.
6. FOR ALL emitted bounds, every non-flagged observed value at the bound's Path SHALL satisfy the bound (soundness property).
7. IF two or more candidates in criterion 2 have equal description length, THEN THE Value_Inferrer SHALL select the candidate nearest to the observed extreme, treating omission of the bound as the farthest candidate.
8. WHERE the bound generalization Technique is disabled, THE Value_Inferrer SHALL emit no `minimum`, `maximum`, `minLength`, `maxLength`, `minItems`, `maxItems`, `minProperties`, or `maxProperties` Constraint, as the Fallback_Behavior for criteria 1, 3, 4, and 5.

### E. Robustness and Versioning

### Requirement 17: Robustness to Bad Documents

**User Story:** As a researcher, I want a few malformed or anomalous documents set aside instead of loosening the schema, so that the schema reflects the bulk of the data.

#### Acceptance Criteria

1. WHERE the Isolation Forest or Local Outlier Factor Technique is enabled, THE Outlier_Detector SHALL compute, with each enabled one of these Techniques, an anomaly score for every parsed document from structural and value features, where a larger score indicates a more anomalous document, and SHALL flag as a Flagged_Item exactly those documents whose score from at least one enabled such Technique strictly exceeds that Technique's Learned_Threshold.
2. WHERE the MDL exception encoding Technique is enabled, THE Outlier_Detector SHALL decide, for each non-flagged value at a Path, between flagging the value as a Flagged_Item and widening the Constraints of the Path to accept the value, by choosing the alternative whose Schema_Model the MDL_Scorer assigns the smaller description length in bits, with ties resolved in favor of widening the Constraints.
3. WHERE the MDL exception encoding Technique is enabled, THE Outlier_Detector SHALL decide, for each structural form among the non-flagged objects at a Path, between flagging every object of that form as a Flagged_Item and adding a Variant for the form, by choosing the alternative whose Schema_Model the MDL_Scorer assigns the smaller description length in bits, with ties resolved in favor of adding the Variant.
4. WHEN a document or value is flagged, THE Inferrer SHALL exclude every Observation belonging to the Flagged_Item from Constraint inference, including from the Support counts in every Provenance_Record, while keeping in Constraint inference the values of the same document that are not part of the Flagged_Item.
5. WHEN a document or value is flagged, THE Inferrer SHALL record one Inference_Report entry for the Flagged_Item containing the document index; the Path, which is the root Path for a whole document; each flagging Technique with its score and the value the score was compared against (the anomaly score and Learned_Threshold for Isolation Forest or Local Outlier Factor, or the two description lengths in bits for MDL exception encoding); and the Constraints the Flagged_Item would have loosened or the Variant it would have added, or an empty list if it would have done neither.
6. WHILE the Isolation Forest, Local Outlier Factor, and MDL exception encoding Techniques are all disabled, THE Inferrer SHALL include every Observation of every parsed document in Constraint inference and report zero Flagged_Items in the Inference_Report.
7. WHILE the Isolation Forest and Local Outlier Factor Techniques are both disabled, THE Inferrer SHALL apply as Fallback_Behavior the inclusion of every parsed document in Constraint inference, excluding only the values flagged under criteria 2 and 3.
8. WHILE the MDL exception encoding Technique is disabled, THE Inferrer SHALL apply as Fallback_Behavior the inclusion in Constraint inference of every value of every document that is not flagged under criterion 1.
9. IF at least one document is parsed and the Flagged_Items would make every parsed document a Flagged_Document, THEN THE Inferrer SHALL discard every Flagged_Item, include every Observation of every parsed document in Constraint inference, and record in the Inference_Report that outlier exclusion was abandoned and how many Flagged_Items were discarded.

### Requirement 18: Schema Versions over Time

**User Story:** As a researcher, I want structural changes over time detected and emitted as schema versions, so that one schema does not blur several generations of the data.

#### Acceptance Criteria

1. WHERE the change-point detection Technique is enabled, THE Version_Detector SHALL compute structural features for each non-flagged document and identify change points in the sequence of those features in Ordering_Key order. The features are the set of Paths present in the document and the JSON types observed at each of those Paths. A change point is a boundary between two consecutive documents in Ordering_Key order.
2. WHERE a timestamp Path is configured as the Ordering_Key, THE Version_Detector SHALL order documents in ascending chronological order of the date or date-time values at the configured Path, and SHALL order documents with equal values by ascending document index.
3. IF no Ordering_Key is configured and one or more Paths with Format `date-time` or `date` have exactly one Observation in every document, THEN THE Version_Detector SHALL select one of those Paths as the Ordering_Key and record the selected Path in the Inference_Report. The selected Path is the one with the fewest steps. Ties are broken by lexicographic order of the Path's steps.
4. IF no Ordering_Key is configured and no Path with Format `date-time` or `date` has exactly one Observation in every document, THEN THE Version_Detector SHALL use the document index as the Ordering_Key and record that choice in the Inference_Report.
5. THE Version_Detector SHALL select the number of change points, zero included, with a penalized-likelihood or MDL criterion and without a user-supplied count. Any penalty weight or minimum segment length used SHALL be a Learned_Threshold. THE Version_Detector SHALL record in the Inference_Report the selected number of change points, the criterion value of the selected segmentation, and the criterion value of the segmentation with no change points.
6. WHEN one or more change points are accepted, THE Inferrer SHALL emit exactly one Schema_Version per segment, giving one more Schema_Version than the number of accepted change points. The segments SHALL be contiguous, non-overlapping ranges in Ordering_Key order that together contain every document. Each Schema_Version SHALL be inferred only from the non-flagged documents of its segment. Each Schema_Version SHALL be labeled with the document index and the Ordering_Key value of the segment's first and last document in Ordering_Key order.
7. WHEN Schema_Versions are emitted, THE Inferrer SHALL emit a diff for each pair of consecutive Schema_Versions that lists added, removed, and changed Constraints. A Constraint is added if its keyword appears at a Path in the later Schema_Version but not at that Path in the earlier one. It is removed in the reverse case. It is changed if the same keyword at the same Path has a different value in the two Schema_Versions.
8. WHEN Schema_Versions are emitted, THE Inferrer SHALL emit a combined schema whose top-level `anyOf` contains exactly one branch per Schema_Version, in the Ordering_Key order of the segments.
9. WHEN the Version_Detector accepts no change point, THE Inferrer SHALL emit a single schema inferred from all non-flagged documents and SHALL emit no Schema_Versions, diffs, or combined schema.
10. WHERE the change-point detection Technique is disabled, THE Inferrer SHALL apply the Fallback_Behavior: it emits a single schema inferred from all non-flagged documents, emits no Schema_Versions, diffs, or combined schema, and records in the Inference_Report that change-point detection was not applied.
11. WHERE a timestamp Path is configured as the Ordering_Key, IF the configured Path has no Observation, has more than one Observation, or has a value that cannot be parsed as a date or date-time in one or more documents, THEN THE Version_Detector SHALL use the document index as the Ordering_Key. It SHALL record in the Inference_Report the configured Path, the fallback to document index, and the number of documents that caused the fallback.

### F. Decisions and Learning

### Requirement 19: MDL-Based Selection

**User Story:** As a researcher, I want choices between alternative schemas made by Minimum Description Length, so that decisions follow one principled criterion instead of magic numbers.

#### Acceptance Criteria

1. THE MDL_Scorer SHALL compute the description length of a candidate Schema_Model and a set of Observations as the sum of the model bits (the bits to encode the Schema_Model) and the data bits (the bits to encode the Observations given the Schema_Model), and SHALL report the model bits, the data bits, and the sum, each as a finite, non-negative number of bits.
2. THE MDL_Scorer SHALL charge a positive, finite exception cost for each Observation that a candidate rejects and SHALL include the exception costs in the candidate's data bits, so that candidates that reject Observations remain comparable with candidates that accept every Observation.
3. WHERE the MDL selection Technique is enabled, WHEN a Decision_Point has two or more candidates and no enabled Decision_Model serves the Decision_Point, THE Inferrer SHALL score every candidate with the MDL_Scorer against the identical set of Observations at the Paths that the Decision_Point affects, excluding Observations that belong to Flagged_Items, and SHALL select the candidate with the lowest description length.
4. IF two or more candidates at a Decision_Point share the lowest description length, THEN THE Inferrer SHALL select the tied candidate with the fewest model bits, and SHALL break any remaining tie first by the Technique priority order documented in the registry and then by a documented candidate order that does not depend on document order or on the number of worker processes.
5. WHEN the Inferrer resolves a Decision_Point by description length, THE Inferrer SHALL record, for the selected candidate and for each rejected candidate, the producing Technique, the model bits, the data bits, the total exception cost, the number of Observations the candidate rejects, the description length, and the number of Observations scored, in the Inference_Report entry for the Decision_Point and in the Provenance_Records of every Constraint that the selected candidate produces.
6. THE MDL_Scorer SHALL return bit-identical description lengths for the same candidate Schema_Model and the same multiset of Observations, independent of the number of worker processes and of the order in which documents are supplied.
7. WHERE the MDL selection Technique is disabled, WHEN a Decision_Point has two or more candidates and no enabled Decision_Model serves the Decision_Point, THE Inferrer SHALL apply the Fallback_Behavior of selecting the candidate ranked first by the Technique priority order documented in the registry, with candidates from the same Technique ordered by the documented candidate order of criterion 4, and SHALL record in the Provenance_Records of the resulting Constraints that the Fallback_Behavior was applied.

### Requirement 20: Learned Thresholds

**User Story:** As a researcher, I want every unavoidable threshold learned from data and recorded, so that no decision depends on an unexplained constant.

#### Acceptance Criteria

1. THE Inferrer SHALL obtain every cut-off used at a Decision_Point from exactly one of four sources: an MDL comparison computed by the MDL_Scorer, a penalized-likelihood model-selection criterion (for example BIC), a Decision_Model comparison of the calibrated probabilities that a Decision_Model assigns to the candidate outcomes, or a Learned_Threshold. This includes every cut-off used inside a Fallback_Behavior.
2. THE Inferrer SHALL read every Learned_Threshold from a single registry, and SHALL provide an enumeration of every registered Learned_Threshold through both the command-line interface and the Python library API. For each Learned_Threshold, the enumeration SHALL give its name, the Technique and Decision_Point kind that use it, and its value in the loaded Model_Bundle.
3. THE Trainer SHALL fit each Learned_Threshold by optimizing the objective recorded for it under criterion 4, using only examples from the validation split of the Training_Data and no example derived from a Held_Out_Schema.
4. THE Trainer SHALL record the following in the Model_Bundle for each Learned_Threshold: its name, the Technique and Decision_Point kind that use it, the objective, the admissible value range, the fitted value, the objective value achieved at the fitted value, the number of validation-split examples used, and the identifier of the Training_Data.
5. THE Inferrer SHALL list in the Inference_Report every Learned_Threshold and every Resource_Parameter read during the run, with its name and value. For each Learned_Threshold, the listing SHALL also give the identifier of the Model_Bundle that supplied it. For each Resource_Parameter, the listing SHALL also state whether the value is the default or was supplied by the user in the Run_Configuration.
6. IF the Model_Bundle lacks a Learned_Threshold required by an enabled Technique, or the stored value is not a finite number within the admissible range recorded under criterion 4, THEN THE Inferrer SHALL apply that Technique's Fallback_Behavior at every affected Decision_Point and complete the run. THE Inferrer SHALL also record in the Inference_Report the Learned_Threshold name, the Technique, the reason (missing value or invalid value), and the Fallback_Behavior applied.
7. WHEN the Inferrer resolves a Decision_Point, THE Inferrer SHALL record the cut-off source: "MDL comparison", "Decision_Model comparison", the name of the model-selection criterion, or the name of a registered Learned_Threshold. It SHALL also record the cut-off value for a Learned_Threshold, the scores of the compared alternatives for an MDL or model-selection comparison, or, for a Decision_Model comparison, the calibrated probabilities of the compared outcomes and the identifier of the Decision_Model artifact in the Model_Bundle that produced them (the Decision_Model trained on synthetic labeled examples only, or the Decision_Model trained with weakly labeled examples, Requirement 23). WHEN a Decision_Model assigns equal calibrated probabilities to the compared outcomes and an MDL comparison selects among them (Requirement 22 criterion 12), THE Inferrer SHALL record "MDL comparison" as the cut-off source in place of "Decision_Model comparison", together with the scores of the tied outcomes. For a resolution that applies no cut-off (a constant Fallback_Behavior outcome, or a selection by the Technique priority order documented in the registry with no Learned_Threshold applied), THE Inferrer SHALL instead record that no cut-off was applied. This record SHALL go in the Provenance_Record of each Constraint that the outcome produces, or in the Inference_Report if the outcome produces no Constraint.
8. IF the validation split of the Training_Data contains no examples for the Decision_Point kind served by a Learned_Threshold, THEN THE Trainer SHALL leave that Learned_Threshold out of the Model_Bundle, record its name and the reason it was left out in the training manifest, and continue producing the remaining Model_Bundle artifacts.

### Requirement 21: Training Pipeline and Model Bundle

**User Story:** As a researcher, I want a reproducible training pipeline that packages every learned artifact, so that inference runs and experiments are traceable to the data they were trained on.

#### Acceptance Criteria

1. WHEN a training run completes, THE Trainer SHALL write a Model_Bundle containing one Decision_Model per Judgment_Call kind, the label model, the Semantic_Type_Classifier, the Learned_Thresholds, the Corpus_Index, and the training manifest, except artifacts omitted under criterion 9, and SHALL assign the Model_Bundle a unique identifier recorded in the training manifest.
2. WHEN the Trainer writes a Model_Bundle, THE Trainer SHALL record in the training manifest the source identifier of every schema used, grouped by training split and validation split; the identifier of every unlabeled Document_Collection given to the Weak_Supervision_Module; every excluded schema with the exclusion reason; the identifier and seed of the Schema_Split; the software version of the Trainer; and the complete training configuration and seed.
3. THE Trainer SHALL fit the parameters of the Decision_Models, the label model, and the Semantic_Type_Classifier only on examples derived from training-split schemas and, where the weak supervision Technique is enabled, from unlabeled Document_Collections, and SHALL use examples derived from validation-split schemas only for probability calibration, Learned_Threshold fitting, and the metrics in criterion 5.
4. THE Trainer SHALL fit the probability calibration of each Decision_Model and of the Semantic_Type_Classifier on validation-split examples only, and store each of these models in the Model_Bundle with its calibration applied.
5. WHEN a training run completes, THE Trainer SHALL record in the training manifest, for each Decision_Model and for the Semantic_Type_Classifier, the number of validation-split examples, the accuracy, the macro-F1, and the expected calibration error before and after calibration, all computed on the validation split, with the confidence-bin count for expected calibration error set as a Resource_Parameter.
6. THE Trainer SHALL train the Semantic_Type_Classifier on values that the Synthetic_Generator produces for scalar fields of training-split schemas, labeling each field by its declared Format, or, for a field without a declared Format, by the semantic type that a documented mapping assigns to the field's normalized name, or otherwise as having no semantic type.
7. WHEN the Trainer runs twice with the same input schemas, unlabeled Document_Collections, training configuration, and seed, THE Trainer SHALL produce Model_Bundles that yield identical predicted classes and identical calibrated probabilities on a probe set drawn with a fixed seed from validation-split examples, contain identical Learned_Threshold values, and have training manifests that are identical apart from the Model_Bundle identifier and timestamps.
8. IF any schema supplied to the Trainer is assigned to the held-out split or is absent from the Schema_Split, or a training stage raises an unrecoverable error, THEN THE Trainer SHALL exit with a non-zero status, leave no Model_Bundle at the output location, and report an error listing the offending schema identifiers or naming the failed stage.
9. IF the training split or the validation split yields no labeled examples for a Judgment_Call kind or for the Semantic_Type_Classifier, or the Technique that produces an artifact is disabled in the training configuration, THEN THE Trainer SHALL omit the affected artifact from the Model_Bundle, write the remaining artifacts, and record each omitted artifact with the reason in the training manifest.
10. IF the Model_Bundle lacks a Decision_Model, the Semantic_Type_Classifier, or the Corpus_Index required by an enabled Technique, THEN THE Inferrer SHALL apply the Fallback_Behavior of the Technique and record the substitution in the Inference_Report.

### Requirement 22: Learned Judgment Calls from Synthetic Labeled Data

**User Story:** As a researcher, I want judgment calls learned from labeled synthetic data generated from real schemas, so that decisions such as record-or-map reflect how real schemas are written.

#### Acceptance Criteria

1. WHEN the Trainer requests Training_Data, THE Synthetic_Generator SHALL generate the number of Document_Collections set by a Resource_Parameter from each training-split and validation-split schema and from no Held_Out_Schema, tagging each Document_Collection with the split of its source schema.
2. WHEN the Synthetic_Generator generates a Document_Collection, THE Synthetic_Generator SHALL sample the collection size (at least 1 document), the presence rate of each optional field (in [0, 1]), the array lengths, and the enum value frequency skew for that Document_Collection independently from the distributions in the generator configuration, and record the sampled values for the Document_Collection in the training manifest.
3. THE Synthetic_Generator SHALL generate each scalar value from the first applicable source in this order: (a) a Format-conformant generator, if the field's subschema declares a Format that has one, producing values that the Validator accepts when it treats `format` as an assertion; (b) an `examples`, `default`, or `enum` value that satisfies the field's subschema, drawn first from the field's own declarations in the source schema and otherwise from fields with the same normalized field name in training-split and validation-split schemas of the Schema_Corpus; (c) a value generated from the type and constraints of the field's subschema.
4. WHEN the Synthetic_Generator generates a Document_Collection, THE Synthetic_Generator SHALL resolve `$ref` and derive one ground-truth label per applicable Judgment_Call kind at each Path of the source schema as follows: Record when an object subschema declares `properties`, and Map when it declares `patternProperties` or a schema-valued `additionalProperties` without `properties`; closed Record when a Record subschema declares `additionalProperties: false`, and open Record when it declares `additionalProperties` as `true` or as a schema; Tuple when an array subschema declares `prefixItems`, and List when it declares `items` without `prefixItems`; Closed_Enum when a scalar subschema declares `enum` or `const`, and open enum when a string, integer, or number subschema declares neither; Split when a subschema declares `anyOf` or `oneOf` with two or more object branches, and Merge when the Path has exactly one object subschema.
5. IF the source schema meets none of the conditions in criterion 4 for a Judgment_Call kind at a Path, THEN THE Synthetic_Generator SHALL record the label for that kind and Path as unknown.
6. THE Trainer SHALL exclude from supervised training every example whose label is unknown and every example at a Path that has no Observation in the generated Document_Collection, and record the number of excluded examples per Judgment_Call kind and per exclusion cause in the training manifest.
7. THE Synthetic_Generator SHALL validate every generated document against the source schema with the Validator and emit only documents that the Validator accepts (generator correctness property).
8. IF the Validator cannot compile a source schema, or the Synthetic_Generator produces no accepted document within the per-document attempt budget set as a Resource_Parameter, THEN THE Synthetic_Generator SHALL discard every Document_Collection generated from that schema, record the schema identifier and the exclusion reason in the training manifest, and continue with the remaining schemas.
9. WHEN the Synthetic_Generator runs twice with an identical schema, generator configuration, and seed, THE Synthetic_Generator SHALL produce byte-identical documents in identical order with identical labels, independent of the number of worker processes.
10. THE Trainer SHALL train one Decision_Model per Judgment_Call kind on examples from training-split schemas, using the same feature computation that the Inferrer applies at inference time, so that the Trainer and the Inferrer compute identical features for an identical Document_Collection.
11. IF the training-split examples for a Judgment_Call kind contain no example of one of the kind's two classes, THEN THE Trainer SHALL omit the Decision_Model for that kind from the Model_Bundle and record the omission with the per-class example counts in the training manifest.
12. WHERE the Decision_Model Technique for a Judgment_Call kind is enabled, WHEN the Inferrer resolves a Judgment_Call of that kind at a Path, THE Inferrer SHALL select the class with the higher calibrated predicted probability (resolving equal probabilities with the MDL_Scorer), record that probability as the Confidence in the Provenance_Records of the resulting Constraints, and list the rejected class with its probability as the alternative considered.
13. WHERE the Decision_Model Technique for a Judgment_Call kind is disabled, THE Inferrer SHALL resolve each Judgment_Call of that kind with the Fallback_Behavior of selecting the candidate with the lowest description length computed by the MDL_Scorer.
14. IF the Decision_Model Technique for a Judgment_Call kind is enabled and the Model_Bundle contains no Decision_Model for that kind, THEN THE Inferrer SHALL apply the Fallback_Behavior of criterion 13 to Judgment_Calls of that kind and record the substitution in the Inference_Report.

### Requirement 23: Weak Supervision from Existing Heuristics

**User Story:** As a researcher, I want existing schema-inference heuristics combined as weak supervision, so that unlabeled real data also contributes to training.

#### Acceptance Criteria

1. THE Weak_Supervision_Module SHALL provide at least three Labeling_Functions for each Judgment_Call kind. Each Labeling_Function SHALL have a unique identifier and a named source heuristic drawn from existing heuristics, including JXPlain-style key-count and key-entropy rules, JSONoid-style transformer rules, distinct-value ratios, and MDL comparisons. Each Labeling_Function SHALL return, for one Path, either one outcome of its Judgment_Call kind or an abstention, and SHALL take every numeric cut-off from an MDL comparison or a Learned_Threshold.
2. WHERE the weak supervision Technique is enabled in the training configuration, THE Weak_Supervision_Module SHALL use the Ingestor to read every unlabeled Document_Collection listed in a manifest file, where each manifest entry gives a unique collection identifier and the location of the collection's documents.
3. THE Weak_Supervision_Module SHALL combine Labeling_Function votes into one probabilistic label at each Path of each unlabeled Document_Collection where the Inferrer evaluates a Judgment_Call of a given kind. The combination SHALL use a label model fitted only on Labeling_Function outputs that reads no ground-truth label. Each probabilistic label SHALL give every outcome of that kind a probability in [0, 1], with the probabilities summing to 1. THE Weak_Supervision_Module SHALL produce no probabilistic label at a Path where every Labeling_Function of that kind abstains.
4. WHERE the weak supervision Technique is enabled in the training configuration, THE Trainer SHALL train, for each Judgment_Call kind with at least one weakly labeled example, a second Decision_Model in addition to the Decision_Model of Requirement 22 criterion 10, and store both in the Model_Bundle. The second Decision_Model SHALL be trained on features computed as in Requirement 22 criterion 10, from two sources: the training-split synthetic labeled examples, each with weight 1, and the weakly labeled examples, each labeled with its highest-probability outcome and weighted by that probability. THE Trainer SHALL exclude weakly labeled examples whose highest probability is shared by two or more outcomes, and SHALL never add weakly labeled examples to the validation-split examples.
5. WHEN training completes, THE Trainer SHALL report the following for each Labeling_Function: coverage, meaning the fraction of the Paths of criterion 3 for its kind at which it votes; conflict rate, meaning the fraction of its voted Paths at which another Labeling_Function of the same kind votes a different outcome; estimated accuracy from the label model; and measured accuracy, meaning the fraction of its votes that match the ground-truth label on validation-split synthetic collections, excluding unknown labels, or reported as undefined when it casts no such vote. THE Trainer SHALL also report the number of weakly labeled examples used for each Judgment_Call kind.
6. WHEN the Weak_Supervision_Module reads the manifest file of criterion 2, THE Trainer SHALL exclude every listed Document_Collection whose identifier matches a Real_Dataset defined for the Evaluation_Harness under Requirement 33. From the remaining collections, THE Trainer SHALL remove every document equal as a parsed JSON value to a document of any such Real_Dataset. THE Trainer SHALL record the excluded identifiers and the number of removed documents in the training manifest.
7. IF a manifest entry has a duplicate identifier, its documents cannot be read, or its Document_Collection contains no parseable document, THEN THE Weak_Supervision_Module SHALL exclude the entry, record the identifier and the reason in the training manifest, and continue with the remaining entries.
8. WHERE the weak supervision Technique and the Decision_Model of a Judgment_Call kind are both enabled in the Run_Configuration, WHEN the Model_Bundle contains a Decision_Model of that kind trained with weakly labeled examples, THE Inferrer SHALL resolve Judgment_Calls of that kind with that Decision_Model.
9. IF the Decision_Model of a Judgment_Call kind is enabled and either the weak supervision Technique is disabled in the Run_Configuration or the Model_Bundle contains no Decision_Model of that kind trained with weakly labeled examples, THEN THE Inferrer SHALL apply the Fallback_Behavior of resolving Judgment_Calls of that kind with the Decision_Model trained on synthetic labeled examples only. THE Inferrer SHALL record in the Inference_Report which Decision_Model resolved each Judgment_Call kind.

### G. Schema Corpus

### Requirement 24: Corpus-Driven Constraint Suggestions

**User Story:** As a researcher, I want a corpus of real schemas to suggest constraints for familiar fields, so that the schema benefits from how others typed the same fields.

#### Acceptance Criteria

1. THE Trainer SHALL build the Corpus_Index from training-split Schema_Corpus schemas only and store the Corpus_Index in the Model_Bundle. For each normalized field name, both alone and paired with the normalized name of the nearest enclosing property (the parent-key context), the Corpus_Index SHALL record the number of field definitions with that name and how many of those definitions declare each Constraint.
2. THE Corpus_Advisor SHALL normalize each field name before lookup with the same normalization the Trainer applies before indexing. The normalization splits the name into tokens at underscores, at hyphens, and at each transition from a lowercase letter or digit to an uppercase letter, then lowercases every token. As a result, `emailAddress`, `email_address`, `email-address`, and `EMAIL_ADDRESS` have the same normalized name.
3. WHERE the name-based suggestion Technique is enabled, WHEN a Path ends in an object-key step whose normalized name equals the normalized field name of at least one Corpus_Index entry, THE Corpus_Advisor SHALL suggest each associated Constraint with a Confidence equal to the Constraint's conditional frequency, ranked by descending conditional frequency with ties broken in a deterministic order. The conditional frequency is the fraction of matching field definitions that declare the Constraint. It is computed over the matching entries whose parent-key context equals the Path's nearest preceding normalized object-key step when at least one such entry exists, and over all name-matching entries otherwise.
4. WHERE the collaborative-filtering Technique is enabled, WHEN a Path ends in an object-key step, THE Corpus_Advisor SHALL also suggest Constraints scored in [0, 1] from the co-occurrence of fields and Constraints across training-split Schema_Corpus schemas, with the score used as the suggestion's Confidence. The suggestions are based on the normalized names of the sibling fields observed at the Path's parent object Path, so that a field without a name match can receive suggestions. WHEN both the name-based suggestion Technique and the collaborative-filtering Technique suggest the same Constraint at the same Path, THE Corpus_Advisor SHALL keep only the suggestion with the higher Confidence.
5. WHEN all of the following conditions hold for a suggested Constraint, THE Inferrer SHALL emit the Constraint in the schema object for the Path, subject to criterion 7:
   - the suggestion's Confidence is greater than or equal to the Learned_Threshold for suggestion acceptance;
   - at least one non-flagged value exists at the Path;
   - every non-flagged value at the Path has a JSON type to which the Constraint's keyword applies;
   - the Validator accepts every non-flagged value at the Path against the Constraint, with `format` treated as an assertion.

   The emitted Constraint SHALL carry a Provenance_Record containing the identifier of the suggesting Technique, the Support computed over non-flagged values, and the suggestion's Confidence.
6. IF a suggested Constraint fails any condition of criterion 5, THEN THE Inferrer SHALL leave the Constraint out of the emitted schema and list the suggestion in the Inference_Report as rejected. The entry SHALL include the Path, the Constraint, the suggesting Technique, the Confidence, and the failed condition. When the Validator rejected one or more values, the entry SHALL also include the number of rejected non-flagged values.
7. IF a suggestion that satisfies criterion 5 and another candidate Constraint at the same Path assign the same JSON Schema keyword, THEN THE Inferrer SHALL treat them as alternative candidates at one Decision_Point. THE Inferrer SHALL select one candidate as specified in Requirement 28, criteria 6 and 7, and list each unselected candidate as rejected in the Inference_Report.
8. WHERE the name-based suggestion Technique or the collaborative-filtering Technique is disabled, THE Corpus_Advisor SHALL apply the Fallback_Behavior of producing no suggestions from the disabled Technique. The Constraints at affected Paths SHALL then come only from the remaining enabled Techniques, and no suggestion from the disabled Technique SHALL appear in the emitted schema or the Inference_Report.
9. WHERE the name-based suggestion Technique or the collaborative-filtering Technique is enabled, IF the Model_Bundle lacks a Corpus_Index, THEN THE Inferrer SHALL apply the Fallback_Behavior in criterion 8 for each enabled suggestion Technique, continue inference, and record the substitution in the Inference_Report.

### Requirement 25: Nearest Known Schema

**User Story:** As a researcher, I want the closest known schema reported for each inferred schema, so that I can see whether the data matches an existing standard.

#### Acceptance Criteria

1. THE Corpus_Advisor SHALL index every Schema_Corpus schema in the Corpus_Index available to the run, after any exclusion under Requirement 30 criterion 6, by MinHash signatures of the schema's normalized Path set (the Paths of the schema's Schema_Model taken across all branches, with each `$ref` expanded up to a Path depth set as a Resource_Parameter and each object-key step normalized as in Requirement 24 criterion 2), using LSH for candidate retrieval with the MinHash permutation count and the LSH band count set as Resource_Parameters and the hash functions seeded from the Run_Configuration seed.
2. WHEN inference completes, THE Corpus_Advisor SHALL record in the Inference_Report, for the emitted schema or for each Schema_Version when Schema_Versions are produced, the LSH candidates with an exact Jaccard similarity greater than 0, ranked by exact Jaccard similarity (the number of shared normalized Paths divided by the number of normalized Paths in the union of the two sets, a value in [0, 1]) in descending order with ties broken by ascending source identifier, where the top-ranked candidate is the Nearest_Known_Schema and at most the count of next-nearest schemas set as a non-negative integer Resource_Parameter follows it, each listed with the source identifier and the exact Jaccard similarity.
3. WHEN a Nearest_Known_Schema is reported for an emitted schema or Schema_Version, THE Corpus_Advisor SHALL list in the Inference_Report the shared normalized Paths, the normalized Paths present only in the inferred schema, and the normalized Paths present only in the Nearest_Known_Schema, each list in lexicographic order.
4. IF the normalized Path set of the inferred schema or Schema_Version is empty, or no LSH candidate has an exact Jaccard similarity greater than 0, THEN THE Corpus_Advisor SHALL record in the Inference_Report that no nearest known schema was found for that schema or Schema_Version and SHALL list no next-nearest schemas for it.
5. WHERE the nearest-known-schema lookup Technique is disabled, THE Corpus_Advisor SHALL skip indexing and lookup and record in the Inference_Report that the lookup was disabled, as a status distinct from the not-found result of criterion 4, and THE Inferrer SHALL emit a schema and explanation file byte-identical to those of the same run with the Technique enabled.
6. IF the Corpus_Index available to the run contains no Schema_Corpus schema, THEN THE Corpus_Advisor SHALL skip the lookup and record in the Inference_Report that the lookup was skipped because the Corpus_Index is empty, without changing the emitted schema or the exit status of the run.
7. FOR ALL Schema_Corpus schemas indexed under criterion 1, a lookup whose normalized Path set equals the normalized Path set of that schema SHALL report a Nearest_Known_Schema with an exact Jaccard similarity of 1.0 (self-retrieval property).

### H. Explainability and Operation

### Requirement 26: Per-Constraint Provenance

**User Story:** As a researcher, I want every inferred constraint explained by method, support, and confidence, so that I can audit and compare how each part of the schema was derived.

#### Acceptance Criteria

1. THE Inferrer SHALL attach exactly one Provenance_Record to every Constraint in each emitted schema and each Schema_Version. This includes Constraints produced by a Fallback_Behavior or a Baseline_Rule, Constraints accepted from the Corpus_Advisor under Requirement 24, criterion 5, and Constraints relaxed under Requirement 3, criterion 3.
2. THE Inferrer SHALL record three items in each Provenance_Record: the producer of the Constraint, which is the identifier of the producing Technique as registered under Requirement 28, criterion 1, the Fallback_Behavior record of criterion 10 and Requirement 28, criterion 12, or the Baseline_Rule marker of criterion 13; the Support; and the Confidence as a number in [0, 1]. The Support SHALL be computed over the non-flagged Observations at the Constraint's Path in the documents covered by the Constraint's schema or Schema_Version. The consistent count SHALL NOT exceed the total count, and the ratio SHALL equal the consistent count divided by the total count. For a Constraint inside a Shared_Definition, the counts SHALL include the Observations at every Path that references the Shared_Definition.
3. WHEN the Inferrer resolves a Decision_Point that has two or more candidates, THE Inferrer SHALL record the following in the Provenance_Record of each resulting Constraint: the resolution method (MDL_Scorer, Decision_Model, Technique priority order under Requirement 28, criterion 7, or Fallback_Behavior), the selected candidate, and every rejected candidate. Each candidate's score SHALL be its description length in bits when the MDL_Scorer resolved the Decision_Point, its calibrated predicted probability in [0, 1] when a Decision_Model resolved the Decision_Point, and absent when Technique priority order or a Fallback_Behavior resolved the Decision_Point.
4. WHEN a Technique derives a Constraint from a seeded random sample under Requirement 29, criterion 8, THE Inferrer SHALL record in the Provenance_Record the number of sampled Observations and the total number of non-flagged Observations at the Path. The Support SHALL still be computed over all non-flagged Observations as stated in criterion 2.
5. THE Schema_Emitter SHALL write one explanation file per run as a JSON document that contains every Provenance_Record of the run. Each Provenance_Record SHALL be keyed by the JSON Pointer of the keyword, or of the array element within a keyword, that expresses the Constraint in the run's top-level emitted schema. The top-level emitted schema is the single schema of Requirement 18, criterion 9, or the combined schema of Requirement 18, criterion 8.
6. WHERE inline annotation is enabled in the Run_Configuration, THE Schema_Emitter SHALL also embed one `x-provenance` keyword in each schema object that contains at least one Constraint. That keyword SHALL hold the Provenance_Record of every Constraint in the schema object, and each record SHALL be identical in content to the Constraint's entry in the explanation file of criterion 5.
7. FOR ALL explanation files written by the Schema_Emitter, every key SHALL resolve to exactly one Constraint in the top-level emitted schema of criterion 5, and no key SHALL resolve to an `x-provenance` keyword. Every Constraint in that schema SHALL be the target of exactly one key (resolvability property).
8. FOR ALL explanation files written by the Schema_Emitter, loading the file with the Inferrer and then writing the loaded Provenance_Records again SHALL produce a byte-identical file (round-trip property).
9. WHEN the explain command is invoked with a schema, an explanation file, and a JSON Pointer that resolves to a Constraint in the schema and has an entry in the explanation file, THE Inferrer SHALL print every field of that Constraint's Provenance_Record to standard output as plain text and exit with status zero. The printed fields are the producer of criterion 2 (a Technique identifier, a fallback marker, or a Baseline_Rule marker), the three Support values, and the Confidence, plus any of these that the record contains: fallback indicator, resolution method, candidates with scores, and sample counts.
10. WHEN a Fallback_Behavior produces a Constraint, THE Inferrer SHALL record three items in the Constraint's Provenance_Record: the identifier of the Technique whose Fallback_Behavior was applied, an indicator that the Fallback_Behavior produced the Constraint, and the reason the Fallback_Behavior was applied. The reason is either that the Technique was disabled under Requirement 28, criterion 4, or that a Learned_Threshold was missing under Requirement 20, criterion 6.
11. FOR ALL Schema_Models, the schema emitted with inline annotation enabled and the schema emitted with inline annotation disabled SHALL accept and reject the same documents under the Validator. Loading either schema with the Schema_Loader SHALL yield equal Schema_Models, consistent with the exclusion of `x-provenance` from Schema_Model equality in Requirement 2, criterion 7 (annotation-neutrality property).
12. IF the explain command of criterion 9 fails in any of the following ways, THEN THE Inferrer SHALL print no Provenance_Record, write an error message naming the failed input and the cause, and exit with a non-zero status: the schema or explanation file cannot be read or parsed; the JSON Pointer is syntactically invalid; the JSON Pointer does not resolve to a Constraint in the schema; or the JSON Pointer has no entry in the explanation file.
13. WHEN a Baseline_Rule produces a Constraint, THE Inferrer SHALL record in the Constraint's Provenance_Record a marker naming the Baseline_Rule in place of a Technique identifier, together with the Support and Confidence of criterion 2, and SHALL record no fallback indicator and no resolution method, because a Baseline_Rule is applied in every run and resolves no Decision_Point.

### I. Evaluation Harness

### Requirement 30: Schema Corpus, Splits, and Leakage Prevention

**User Story:** As a researcher, I want schema-level splits with near-duplicate grouping and leakage checks, so that benchmark results reflect generalization to unseen schemas.

#### Acceptance Criteria

1. THE Evaluation_Harness SHALL load the Schema_Corpus from SchemaStore, including the positive and negative test files of each schema, and from JSONSchemaBench. For each schema it SHALL record an identifier that is unique across the Schema_Corpus, a source identifier naming SchemaStore or JSONSchemaBench, and the snapshot version of the source, and it SHALL link each test file to the schema that the file tests.
2. THE Evaluation_Harness SHALL place two schemas in the same near-duplicate group when the schemas are listed as versions of one SchemaStore catalog entry, or when the Jaccard similarity of their normalized Path sets is at or above a cut-off. The cut-off SHALL lie in (0, 1] and SHALL be selected by a model-selection criterion over the pairwise similarities of the Schema_Corpus schemas. Grouping SHALL be transitive. THE Evaluation_Harness SHALL assign all members of a group to the same one of the training, validation, or held-out splits, aiming for the proportions, counted in schemas, set by the training, validation, and held-out split-proportion Resource_Parameters (proposed defaults 0.70, 0.10, and 0.20).
3. THE Evaluation_Harness SHALL assign to the held-out split every schema that serves as the known schema of a Real_Dataset, together with every member of that schema's near-duplicate group. Where the known schema is not itself in the Schema_Corpus, the Evaluation_Harness SHALL instead assign to the held-out split every corpus schema whose similarity to the known schema reaches the cut-off of criterion 2.
4. WHEN the Evaluation_Harness produces the Schema_Split, THE Evaluation_Harness SHALL derive every group and split assignment only from the seed, the loaded Schema_Corpus, the known schemas of the Real_Datasets, and the split-proportion Resource_Parameters, so that two runs with equal inputs produce identical assignments. THE Evaluation_Harness SHALL persist to disk each schema's identifier, near-duplicate group, and split, together with: the seed; the source snapshot versions; the selected cut-off and the criterion that selected it; the configured and realized split proportions, with a deviation flag on each split whose realized share differs from its configured proportion by more than 0.05; and the exclusions recorded under criteria 5 and 9.
5. IF the Validator reports a schema invalid against the meta-schema named by the schema's `$schema` keyword (draft 2020-12 when the keyword is absent), or the schema declares a dialect other than draft-04, draft-06, draft-07, draft 2019-09, or draft 2020-12, or the Schema_Loader marks the schema as partially supported, THEN THE Evaluation_Harness SHALL exclude the schema from synthetic generation, keep the schema in its near-duplicate group and split, and record the schema identifier and the exclusion reason in the persisted Schema_Split.
6. WHILE the Evaluation_Harness evaluates a Held_Out_Schema, THE Corpus_Advisor SHALL exclude the Held_Out_Schema and every member of the Held_Out_Schema's near-duplicate group from the Corpus_Index, so that no suggested Constraint and no Nearest_Known_Schema comes from an excluded schema.
7. WHEN a benchmark run starts, THE Evaluation_Harness SHALL, before running any inference or Baseline, compare every schema identifier and Document_Collection identifier in the training manifest of the Model_Bundle with the schemas of the held-out split, their near-duplicate groups, and the Document_Collections of the Real_Datasets.
8. IF the training manifest lists any schema that belongs to a near-duplicate group of the held-out split, or lists the Document_Collection of any Real_Dataset, THEN THE Evaluation_Harness SHALL abort the run without producing benchmark metrics and report every overlapping schema identifier, near-duplicate group, and Document_Collection identifier.
9. IF a schema file or a SchemaStore test file cannot be read or is not valid JSON, THEN THE Evaluation_Harness SHALL omit the file from the Schema_Corpus (omitting a schema also omits all test files linked to that schema), record each omitted file's identifier and the reason, and continue loading the remaining files.
10. IF any split-proportion Resource_Parameter is not strictly between 0 and 1, or the three proportions do not sum to 1 within 0.001, or the assignment would leave the training, validation, or held-out split with no schema, THEN THE Evaluation_Harness SHALL stop without writing a Schema_Split and report the offending values.
11. IF the Model_Bundle contains no training manifest, or the training manifest lists a schema identifier that is absent from the loaded Schema_Corpus, THEN THE Evaluation_Harness SHALL abort the benchmark run without producing benchmark metrics and report the missing manifest or every unresolved identifier.

### Requirement 31: Synthetic Round-Trip Benchmark

**User Story:** As a researcher, I want to generate documents from held-out schemas, infer schemas, and compare against the truth, so that I can measure accuracy with full ground truth.

#### Acceptance Criteria

1. WHEN the synthetic benchmark runs, THE Evaluation_Harness SHALL generate with the Synthetic_Generator, from the configured seed and for each Held_Out_Schema not excluded from synthetic generation, one training Document_Collection per configured training collection size and one set of held-out Positive_Documents of a configured count (proposed default: 1,000), such that no held-out Positive_Document is equal, as a parsed JSON value, to any document in any training Document_Collection of the same Held_Out_Schema.
2. WHEN a training Document_Collection is generated, THE Evaluation_Harness SHALL run the Inferrer with the default Run_Configuration, and each Baseline not recorded as unavailable, on the Document_Collection, producing one inferred schema per system.
3. THE Evaluation_Harness SHALL compute recall for each inferred schema as the number of the Held_Out_Schema's held-out Positive_Documents that the Validator accepts against the inferred schema, divided by the total number of those held-out Positive_Documents.
4. THE Evaluation_Harness SHALL compute the negative rejection rate for each inferred schema as the number of the Held_Out_Schema's retained Negative_Documents, produced by Mutation_Operators, that the Validator rejects against the inferred schema, divided by the total number of those Negative_Documents.
5. THE Evaluation_Harness SHALL report for each inferred schema the harmonic mean of recall R and negative rejection rate N, computed as 2·R·N / (R + N), and as 0 when R and N are both 0.
6. WHILE computing recall and the negative rejection rate, THE Validator SHALL treat `format` as an assertion for the schema of every evaluated system, regardless of the draft the schema declares, so that a value that violates a declared Format counts as a rejection.
7. IF the Subschema_Checker supports every keyword in both the inferred schema and the ground-truth schema (the Held_Out_Schema), THEN THE Evaluation_Harness SHALL use the Subschema_Checker to test whether each schema is a subschema of the other and, when both tests complete, report the relation as equivalent (both inclusions hold), subset (only the inferred schema is included in the ground-truth schema), superset (only the ground-truth schema is included in the inferred schema), or incomparable (neither inclusion holds).
8. IF either schema contains a keyword that the Subschema_Checker does not support, or an inclusion test raises an error or exceeds the per-check time limit set as a Resource_Parameter, THEN THE Evaluation_Harness SHALL report the inclusion relation as unsupported and record the cause as the list of unsupported keywords, the error, or the timeout.
9. THE Evaluation_Harness SHALL compute, for each inferred schema and each Judgment_Call kind, accuracy as the fraction of the Held_Out_Schema's Paths with a known ground-truth label of that kind at which the inferred schema has the same Path and the same outcome. The inferred outcome SHALL be derived with the same schema-keyword rules the Synthetic_Generator uses to derive ground-truth labels, and a labeled Path absent from the inferred schema SHALL count as incorrect.
10. THE Evaluation_Harness SHALL compute, for each inferred schema and each Constraint kind among required fields, Formats, Closed_Enums, Tagged_Unions, Co_Occurrence_Rules, Exclusion_Rules, and bounds, precision as the fraction of inferred Constraints of the kind that match a ground-truth Constraint, and recall as the fraction of ground-truth Constraints of the kind that match an inferred Constraint. Two Constraints match when they are at the same Path and agree on the field name for required fields, the Format value for Formats, the value set for Closed_Enums, the Discriminator and its value set for Tagged_Unions, the antecedent and implied fields for Co_Occurrence_Rules, the set of mutually exclusive fields or Field_Groups for Exclusion_Rules, and the bound keyword (for example `minimum` or `maxItems`), regardless of bound value, for bounds.
11. THE Evaluation_Harness SHALL take training collection sizes from a configured series of one or more positive integers (proposed default: 10, 100, and 1,000 documents), evaluate every system at every size against the same held-out Positive_Documents and retained Negative_Documents of each Held_Out_Schema, and report every metric per training size to measure sample efficiency.
12. IF the Synthetic_Generator cannot produce, within the attempt budget set as a Resource_Parameter, every configured training Document_Collection and the configured count of held-out Positive_Documents distinct from the training documents for a Held_Out_Schema, THEN THE Evaluation_Harness SHALL exclude the Held_Out_Schema from the synthetic benchmark at every training size and record the exclusion with the reason.
13. IF the Inferrer or a Baseline exits with an error, exceeds the per-run time limit set as a Resource_Parameter, or returns no schema or a schema that the Validator cannot load, THEN THE Evaluation_Harness SHALL record the failure kind for that system, Held_Out_Schema, and training size, report every metric of that combination as missing, continue with the remaining combinations, and report per system the count of missing combinations next to each aggregated metric.
14. IF a metric's denominator is zero for an inferred schema, as when the Held_Out_Schema has no retained Negative_Documents, no Paths with a known label of a Judgment_Call kind, or no Constraints of a kind in the inferred schema (for precision) or the ground-truth schema (for recall), THEN THE Evaluation_Harness SHALL report the metric as undefined rather than 0 or 1, report the harmonic mean as undefined when either of its inputs is undefined, exclude undefined values from aggregates, and report the count of undefined values next to each aggregated metric.

### Requirement 32: Negative Documents by Schema Mutation

**User Story:** As a researcher, I want negative documents created by mutating the true schema, so that I can measure whether inferred schemas reject invalid data and not only accept valid data.

#### Acceptance Criteria

1. THE Evaluation_Harness SHALL provide the following Mutation_Operators. Each has a distinct name, and its applicable site is the schema construct listed with it: (a) remove a required field, applicable at a `required` entry; (b) add an undeclared property, applicable at an object schema with `additionalProperties: false`; (c) change a value's type, applicable at a `type` keyword; (d) replace an enum value with a non-member, applicable at an `enum` or `const` keyword; (e) violate a Pattern, applicable at a `pattern` keyword; (f) violate a Format, applicable at a `format` keyword; (g) violate a numeric bound, applicable at a `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, or `multipleOf` keyword; (h) violate a string length bound, applicable at a `minLength` or `maxLength` keyword; (i) violate a count bound, applicable at a `minItems`, `maxItems`, `minProperties`, or `maxProperties` keyword; (j) reorder Tuple positions, applicable at a `prefixItems` keyword with at least two positions whose subschemas differ; (k) pair a Discriminator value with another branch's fields, applicable at a Tagged_Union in which each branch fixes the Discriminator to a distinct `const` or single-value `enum`; (l) break a Co_Occurrence_Rule, applicable at a `dependentRequired` entry; (m) combine mutually exclusive fields, applicable at an Exclusion_Rule expressed as a `not` over a `required` set or as a `oneOf` across field groups; and (n) duplicate an element, applicable at a `uniqueItems: true` keyword.
2. THE Evaluation_Harness SHALL apply exactly one Mutation_Operator at exactly one applicable site per mutated schema and leave every other part of the ground-truth schema unchanged, so that each Negative_Document isolates one violation kind.
3. WHEN a mutated schema is created, THE Evaluation_Harness SHALL generate candidate documents from the mutated schema with the Synthetic_Generator, validate each candidate against the ground-truth schema with the Validator treating `format` as an assertion, and retain each distinct candidate (by JSON value equality) that the ground-truth schema rejects. Generation SHALL stop when the number of retained Negative_Documents reaches the per-mutated-schema target set as a Resource_Parameter, or when the attempt budget is exhausted. The attempt budget is counted in candidate documents generated per mutated schema and is set as a Resource_Parameter.
4. THE Validator SHALL reject every retained Negative_Document against the ground-truth schema, with `format` treated as an assertion (negative correctness property).
5. THE Evaluation_Harness SHALL label each Negative_Document with the name of the Mutation_Operator that produced it, the identifier of the ground-truth schema, and the JSON Pointer of the mutated site in the ground-truth schema.
6. IF a ground-truth schema contains no applicable site for a Mutation_Operator as defined in criterion 1, THEN THE Evaluation_Harness SHALL skip the Mutation_Operator for the schema and record the skip with the schema identifier and the Mutation_Operator name.
7. IF none of the mutated schemas that a Mutation_Operator creates for a ground-truth schema yields a retained Negative_Document within the attempt budget, including the case where the Synthetic_Generator excludes the mutated schema, THEN THE Evaluation_Harness SHALL record the Mutation_Operator as unproductive for the schema, with the number of candidate documents attempted, and continue with the remaining Mutation_Operators and schemas.
8. WHEN the Evaluation_Harness reports benchmark results, THE Evaluation_Harness SHALL report, for each evaluated system and each Mutation_Operator, the number of Negative_Documents the Mutation_Operator produced and the fraction of those Negative_Documents that the system's inferred schema rejects. IF a Mutation_Operator produced zero Negative_Documents, THEN THE Evaluation_Harness SHALL report its rejection rate as not applicable instead of 0.
9. WHEN a Mutation_Operator has applicable sites in a ground-truth schema, THE Evaluation_Harness SHALL create one mutated schema per applicable site. IF the number of applicable sites exceeds the per-operator site limit set as a Resource_Parameter, THEN THE Evaluation_Harness SHALL instead select a seeded random subset of sites equal to the limit.
10. THE Evaluation_Harness SHALL produce identical mutated schemas and identical Negative_Documents for an identical ground-truth schema, configuration, and seed.

### Requirement 33: Real Data with Known Schemas

**User Story:** As a researcher, I want real datasets with independently authored schemas as the final judge, so that results are not an artifact of my own synthetic generator.

#### Acceptance Criteria

1. THE Evaluation_Harness SHALL accept Real_Dataset definitions from a manifest file, each definition containing a Real_Dataset identifier that is unique within the manifest, a Document_Collection, a known schema, optional Negative_Documents, and an optional Ordering_Key.
2. THE Evaluation_Harness SHALL include as a Real_Dataset each SchemaStore schema that has at least one positive test file, using each positive test file as one document of the Document_Collection and each negative test file as one Negative_Document.
3. THE Evaluation_Harness SHALL evaluate each Real_Dataset by cross-validation over the n positive documents that remain after the exclusions in criterion 5. It SHALL use min(k, n) folds, so that leave-one-out applies when n is less than k, where k is an integer of at least 2 set in the configuration with a default of 5. It SHALL infer one schema per fold from the documents outside that fold, and SHALL assign documents to folds deterministically from the configured seed, with the same assignment for the Inferrer and every Baseline.
4. WHEN a Real_Dataset has no Negative_Documents remaining after the exclusions in criterion 5, THE Evaluation_Harness SHALL generate Negative_Documents by applying the Mutation_Operators of Requirement 32 to the known schema.
5. IF a document or Negative_Document of a Real_Dataset cannot be parsed as JSON, or the known schema rejects a positive document, or the known schema accepts a Negative_Document, with the Validator treating `format` as an assertion, THEN THE Evaluation_Harness SHALL exclude that document from the Real_Dataset and record the Real_Dataset identifier, the document identifier, and the reason (parse failure, positive rejected, or negative accepted).
6. THE Evaluation_Harness SHALL report Real_Dataset results in tables separate from synthetic results, place the Real_Dataset tables before the synthetic tables in every summary output, and label the Real_Dataset tables as the primary comparison. For each Real_Dataset, the report SHALL list n, the number of folds, the number of documents excluded under criterion 5, and whether the Negative_Documents were supplied by the Real_Dataset or generated under criterion 4. The report SHALL also give the number of Real_Datasets excluded under criterion 8 for each reason.
7. THE Evaluation_Harness SHALL compute three metrics for each system and Real_Dataset:
   - Recall: the fraction of the n positive documents accepted by the schema inferred for the fold that holds out the document.
   - Negative rejection rate: the mean, across folds, of the fraction of the Real_Dataset's Negative_Documents that the fold's inferred schema rejects.
   - The harmonic mean of recall and the negative rejection rate.
8. IF a manifest definition lacks a Document_Collection or a known schema, repeats an identifier used by an earlier definition, or references a file that cannot be read, or if any Real_Dataset has a known schema that the Validator cannot use for validation, or has fewer than 2 positive documents remaining after the exclusions in criterion 5, THEN THE Evaluation_Harness SHALL exclude the Real_Dataset from all metrics, record the Real_Dataset identifier with the reason (and, when fewer than 2 positive documents remain, the remaining document count), and continue with the remaining Real_Datasets.
9. IF a Real_Dataset has no Negative_Documents after the generation in criterion 4, THEN THE Evaluation_Harness SHALL report the Real_Dataset's recall, report its negative rejection rate and harmonic mean as not available, leave it out of the aggregate negative rejection rate and harmonic mean, and record the reason.

### Requirement 34: Baselines

**User Story:** As a researcher, I want ReCG, JSONoid, and a naive merge run under identical conditions, so that comparisons with prior work are fair.

#### Acceptance Criteria

1. THE Evaluation_Harness SHALL run JSONoid, ReCG, and Naive_Merge each through a Baseline_Adapter that takes a Document_Collection as input and returns exactly one JSON Schema document.
2. THE Evaluation_Harness SHALL give every Baseline and the Inferrer the same training documents in the same order for each training Document_Collection and each cross-validation fold, and evaluate every returned schema on the same Positive_Documents and Negative_Documents with the same metrics and the same Validator settings.
3. THE Evaluation_Harness SHALL execute Baseline and Inferrer runs one at a time on the same machine and measure the runtime of every run as wall-clock time from run start until the run returns a schema.
4. THE Inferrer SHALL include a Naive_Merge implementation in the project codebase that emits a draft 2020-12 schema using no keywords other than `$schema`, `type`, `properties`, `items`, and `required`, where `type` lists the union of JSON types (`null`, `boolean`, `integer`, `number`, `string`, `array`, `object`) observed at each Path, listing `integer` instead of `number` when every observed number at the Path has a zero fractional part as defined in Requirement 13 criterion 2, `properties` lists the union of keys observed at each object Path, `items` merges all elements observed at an array Path into one subschema, and `required` lists the keys present in every object observed at the Path.
5. WHEN a Baseline returns a schema in draft-04, draft-06, draft-07, or draft 2019-09, as declared by the schema's `$schema` or, if `$schema` is absent, by the output draft recorded in the Baseline's configuration, THE Evaluation_Harness SHALL translate the schema to draft 2020-12 with the Schema_Loader, compute all metrics on the translated schema, and record with the results the source draft, each translated keyword, and each construct the Schema_Loader reports as unsupported.
6. IF a Baseline cannot be started when the benchmark begins, for example because its executable or its language runtime is missing, THEN THE Evaluation_Harness SHALL mark the Baseline as unavailable in every results file and summary table instead of omitting it, and continue with the remaining systems.
7. IF a Baseline or Inferrer run exceeds the per-run time limit set as a Resource_Parameter (default 1800 seconds), THEN THE Evaluation_Harness SHALL terminate the run and every process the run started, record a timeout for the run's system, dataset, and configuration, and continue with the remaining runs.
8. IF a Baseline run exits with a non-zero status or returns output that is not a JSON document valid against the meta-schema of the draft declared by its `$schema` or recorded in the Baseline's configuration, THEN THE Evaluation_Harness SHALL record a failure for the run with the exit status and the captured error output, and continue with the remaining runs.
9. WHEN results are aggregated, THE Evaluation_Harness SHALL exclude runs that ended in a timeout (criterion 7) or failure (criterion 8) from the affected system's metric means, report the number of timeouts and failures per system and dataset group, and compute paired comparisons between the Inferrer and each Baseline only over datasets for which both returned a schema.
10. WHERE a ReCG reimplementation is used in place of the official ReCG implementation, THE Evaluation_Harness SHALL label the system as a ReCG reimplementation in every CSV and JSON results file and every Markdown and LaTeX summary table that reports its results.
11. THE Evaluation_Harness SHALL record with every Baseline result the Baseline's version or commit identifier, every configuration option and command-line argument the Baseline_Adapter passed to the Baseline, and the version of the language runtime that executed the Baseline.

### Requirement 35: Metrics, Studies, and Reporting

**User Story:** As a researcher, I want statistically grounded metrics, ablation, robustness, versioning, and calibration studies, so that I can report which techniques help and by how much.

#### Acceptance Criteria

1. THE Evaluation_Harness SHALL report each metric of Requirements 31–33 and of criterion 7, per system and Dataset_Group, as the mean over the Held_Out_Schemas or Real_Datasets of the Dataset_Group that have a value, together with the count of contributing schemas or datasets and a 95% percentile bootstrap confidence interval computed with a seeded resample count set as a Resource_Parameter, marking the interval as not computable when fewer than two schemas or datasets contribute.
2. THE Evaluation_Harness SHALL report, for each metric, Dataset_Group, and Baseline, a paired bootstrap test over the Held_Out_Schemas or Real_Datasets for which both the Inferrer and the Baseline have a value, giving the mean difference (Inferrer minus Baseline), the 95% percentile bootstrap confidence interval of the difference, the two-sided p-value, and the number of pairs, using the resample count of criterion 1 and marking the test as not computable when fewer than two pairs exist.
3. WHEN an ablation study runs, THE Evaluation_Harness SHALL create one ablated Run_Configuration for each Technique enabled in the default Run_Configuration by disabling that Technique, run the Inferrer under the default and every ablated Run_Configuration on the same Document_Collections with the same seed, and report, for each metric and Dataset_Group, the difference (ablated minus default) with the confidence interval and p-value computed as in criterion 2.
4. WHEN a robustness study runs, THE Evaluation_Harness SHALL, for each contamination rate strictly between 0 and 1 in the series set as a Resource_Parameter, add seeded randomly selected corrupted documents to each training Document_Collection until they form that fraction of the resulting collection, run the Inferrer and every available Baseline on the contaminated collection, and report the change in recall, the change in negative rejection rate, and the number of loosened Constraints relative to the uncontaminated run, where corrupted documents are Negative_Documents produced per Requirement 32 and disjoint from the Negative_Documents used for measurement, and a loosened Constraint is a Constraint of the uncontaminated schema that is absent at the same Path in the contaminated schema or present there with a widened bound, an added JSON type, or an added enum member.
5. WHEN a versioning study runs, THE Evaluation_Harness SHALL concatenate a Document_Collection generated from a Held_Out_Schema with a Document_Collection generated from a successor schema produced from it by Mutation_Operators, run the Inferrer with the change-point detection Technique enabled and the document index as the Ordering_Key, and report the number of accepted change points, the change-point location error as the absolute difference in document index between the true boundary and the nearest accepted change point, and, for each true segment, the harmonic mean of recall and negative rejection rate of the Schema_Version whose segment shares the most documents with the true segment, measured with held-out Positive_Documents and Negative_Documents of that segment's source schema.
6. THE Evaluation_Harness SHALL compute, for the Inferrer on the synthetic benchmark over Held_Out_Schemas, reliability-curve data over equal-width Confidence bins on [0, 1], with the bin count set as a Resource_Parameter, giving for each bin the Constraint count, the mean Confidence, and the fraction correct, where each emitted Constraint of a kind listed in Requirement 31 criterion 10 is correct when the ground-truth schema contains the same Constraint at the aligned Path, and SHALL compute the expected calibration error as the count-weighted mean absolute difference between mean Confidence and fraction correct over the non-empty bins, reporting empty bins with a count of zero.
7. THE Evaluation_Harness SHALL report, for every system and dataset, the wall-clock runtime in seconds, the peak resident memory in megabytes of the system's process and its child processes, the schema size as the number of JSON Schema keyword occurrences in the emitted schema including those under `$defs`, and the description length in bits that the MDL_Scorer computes for the emitted schema, loaded with the Schema_Loader, together with the system's training Document_Collection.
8. THE Evaluation_Harness SHALL write per-schema, per-dataset, and aggregated results as both CSV and JSON files containing identical values, each result identifying the system, dataset, Run_Configuration, and seed, and SHALL write summary tables of the aggregates of criteria 1–3 in both Markdown and LaTeX.
9. WHEN an interrupted benchmark restarts with the same configuration and seed, THE Evaluation_Harness SHALL reuse, without re-running any system, the stored results of every (system, dataset, configuration) combination completely written before the interruption, and SHALL discard and recompute the results of every combination that was absent or partially written.
10. IF disabling a Technique for an ablation run leaves an enabled Technique without a prerequisite Technique, THEN THE Evaluation_Harness SHALL also disable, transitively, every such dependent Technique in that ablated Run_Configuration and record the complete set of disabled Techniques with the ablation results.
11. IF the Version_Detector accepts no change point in a versioning study run, THEN THE Evaluation_Harness SHALL record the run as a missed change point, exclude the run from the change-point location error, report the fraction of missed runs, and compute the per-segment harmonic means of criterion 5 against the single emitted schema.
12. IF a system produces no schema for a Held_Out_Schema or Real_Dataset because of unavailability, timeout, or error, or a metric cannot be computed for the system's schema, THEN THE Evaluation_Harness SHALL record each affected metric value as missing with the reason, exclude the missing values from the aggregates of criteria 1–3, and report the count of missing values per system, metric, and Dataset_Group.
